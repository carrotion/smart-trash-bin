# ATS 서버 쪽 작업 — 인계 문서

> 로봇(Pi5, `smart-bin-01`)에서 작업하는 에이전트가 2026-08-17에 작성.
> 서버(윈도우 PC, `192.168.0.170`)에서 작업할 에이전트를 위한 문서다.

## 0. 협업 방식 — 계약을 먼저 고정한다

**실시간 채널 대신 이 저장소(git)를 통해 비동기로 협업한다.** 서로 기다리지 않고,
결정과 근거가 기록으로 남는다. `git@github.com:carrotion/smart-trash-bin.git`

경계는 **아래 3장의 HTTP 계약 하나**다. 양쪽이 이것만 지키면 서버를 어떻게 구현하든
로봇은 알 필요가 없고, 반대도 마찬가지다.

> ⚠️ **계약을 바꾸려면 반드시 이 문서를 같은 커밋에서 고칠 것.**
> 로봇 쪽(`tools/artifact_uploader.py`)과 서버 쪽이 조용히 어긋나면, 로봇이
> "올렸다"고 믿고 로컬에서 지운 뒤 서버엔 없는 상황이 생긴다. 성과물 유실이다.

## 1. 이미 끝난 것 — 다시 만들지 말 것

| 파일 | 상태 |
|---|---|
| `server/ats_receiver.py` | **완성·검증됨.** 표준 라이브러리만 사용, 설치 불필요 |
| `tools/artifact_uploader.py` | **완성·검증됨.** 로봇에서 동작 중 |

로봇에서 양쪽을 다 띄워 실제로 통과시킨 시험:

| 시험 | 결과 |
|---|---|
| 정상 업로드(맵 pgm/yaml, 지표 json) | 우선순위 순으로 전송, 기체별 보관, 로컬은 확인 후 `sent/`로 이동 |
| 서버 다운 | 우아하게 실패, `outbox/`에 보존, 로봇 동작 무영향 |
| 경로 탈출 `../../etc/passwd` | `unknown-unit/misc/...`로 무해화, 탈출 없음 |
| 체크섬 불일치 | 422 거부, 손상 파일 저장 안 함 |
| 윈도우 예약 장치명(`NUL`,`CON`,`COM1`) | 차단, 대체 이름으로 보존 |
| 거부된 이름 다건 동시 도착 | 난수 접미사로 서로 덮어쓰지 않음 |

## 2. 서버에서 지금 할 일

### 2.1 수신기 상시 가동 (최우선)

```
python server\ats_receiver.py --root "C:\Users\carro\projects\smart-trash-bin\artifacts" --port 8080
```

- **작업 스케줄러**에 등록(윈도우엔 systemd가 없다). 트리거 "시스템 시작 시",
  "작업이 실패하면 다시 시작" 켜기
- **방화벽 8080 인바운드 허용** — 안 하면 로봇이 접속 못 한다
  ```powershell
  New-NetFirewallRule -DisplayName "ATS receiver" -Direction Inbound `
    -LocalPort 8080 -Protocol TCP -Action Allow -Profile Private
  ```
- 보관 경로를 `artifacts\` 하위로 둔 이유: 프로젝트 폴더에 기존 산출물이 이미
  있어서, 자동 업로드분과 섞이면 나중에 구분이 안 된다

확인: `http://192.168.0.170:8080/` (보관 현황), `/api/list` (JSON)

### 2.2 그다음 — 우선순위 순

`docs/agent_architecture.md` 4장의 순서를 따른다.

1. **통합 대시보드** — 지금 `/` 페이지는 파일 목록뿐이다. 기체별 상태, 맵 미리보기
   (pgm 렌더링), 주행 이력, 품질 지표 추이로 확장할 것
2. **기체별 백업/복원** — 유닛 설정·보정값. 로봇 SD가 죽어도 복구 가능해야 한다
3. **맵 저장소와 공유** — 한 기체가 만든 맵을 다른 기체에 배포. 버전/이력 관리
4. **재생 실험 harness** — 로봇의 `tools/replay_slam.py`를 서버로 옮기는 것.
   파이는 3배속 재생도 버겁다. 서버면 **파라미터 조합을 병렬로** 돌려 비교할 수 있다.
   ⚠️ ROS 2 Jazzy 필요 — 윈도우면 WSL2나 Docker 검토

## 3. HTTP 계약 (고정 인터페이스)

### 업로드

```
POST /upload?unit=<기체ID>&kind=<종류>&name=<파일명>&sha256=<로컬해시>
Content-Type: application/octet-stream
Content-Length: <바이트>
본문: 파일 원본 바이트
```

- `kind`: `telemetry` | `metrics` | `maps` | `bags` (로봇이 이 순서로 올린다 —
  작고 중요한 것 먼저. 링크가 잠깐만 살아도 핵심이 넘어가도록)
- `bags`는 디렉터리라 로봇이 **tar로 묶어** 보낸다(`.tar`)

**응답 200**
```json
{"ok": true, "sha256": "<서버가 받은 내용을 다시 계산한 해시>",
 "bytes": 12345, "stored": "unit/kind/name"}
```

> 🔑 **이 `sha256`이 계약의 핵심이다.** 로봇은 자기 값과 **일치할 때만** 로컬에서
> 파일을 치운다. 그러니 서버는 **받은 내용을 실제로 다시 읽어서** 계산해야 한다.
> 보낸 값을 그대로 되돌려주면 전송 손상을 못 잡고, 로봇은 깨진 파일을 올려놓고
> 원본을 지운다.

**오류 응답**

| 코드 | 뜻 | 로봇 동작 |
|---|---|---|
| 400 | Content-Length 이상 / 본문 없음 / 수신 미완 | 재시도 |
| 413 | 2GB 초과 | 재시도(계속 실패하면 사람이 봐야 함) |
| 422 | 체크섬 불일치 | 재시도. **로컬 파일은 유지된다** |
| 500 | 서버 쓰기 실패 | 재시도 |

### 조회

```
GET /            보관 현황 HTML
GET /api/list    {unit: {kind: [{name, bytes, mtime}, ...]}}
```

## 5. 로봇 쪽 제약 — 서버를 설계할 때 반드시 감안할 것

이건 취향이 아니라 실측된 제약이다. 자세한 근거는 `docs/agent_architecture.md`.

1. **로봇은 서버를 절대 기다리지 않는다.** 서버가 죽어 있어도 로봇은 정상 동작해야
   한다. 서버 응답을 로봇 동작의 전제로 삼는 기능을 제안하지 말 것
2. **로봇은 자주 오프라인이다.** 주방 WiFi 음영지역이 실재한다. 끊김은 예외가
   아니라 정상 상태다
3. **비상정지·수동조종·블랙박스 기록은 절대 서버로 옮기지 않는다.**
   비상정지는 하루를 들여 버그 3개를 잡은 기능이고, 네트워크를 경유시키면 실패
   경로가 하나 더 생긴다. 블랙박스는 **통신이 끊긴 순간을 기록**하는 것이라
   그 기록을 통신으로 보낼 수는 없다
4. **로봇 SD 수명이 제약이다.** 업로드 때문에 로봇에 사본을 만들게 하지 말 것
5. **과설계 금지.** 유닛 3대 규모다. HTTP + 파일 저장 + 정적 페이지면 충분하다
