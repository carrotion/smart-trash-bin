## 0. 왜 이 경계가 필요한가 — 오늘 실제로 겪은 것

추측이 아니라 2026-08-17 하루에 관측된 사실에서 나온 설계다.

| 사건 | 드러난 문제 |
|---|---|
| 주방에서 갇히고 **동시에 통신 두절** | 관측이 가장 필요한 순간에 아무것도 못 봤다 |
| 전원 3회 차단, 프리즈 2회 | 사고 기록이 **로봇 SD 안에만** 있다. 카드가 죽으면 같이 사라진다 |
| 대시보드 5개가 로봇에서 동작(8764~8768) | SLAM/Nav2와 **같은 CPU를 두고 경쟁**한다. 프리즈의 방아쇠가 CPU 부하였다 |
| 조종 주행 맵 158.3 m², 가방 29.5 MB, 정렬도 71.2% | 오늘의 성과물이 **전부 이 기체 안에만** 있다. 2호기와 비교할 방법이 없다 |
| 재생 실험 도구를 파이에서 돌림 | 3배속 재생조차 버겁다. **이런 계산은 서버가 할 일**이다 |

## 1. 경계를 가르는 원칙

> **네트워크가 끊겨도 로봇이 계속 동작해야 하는 것은 로컬.
> 모아야 비로소 가치가 생기는 것은 서버.**

이 로봇은 **자주 오프라인이다.** WiFi 음영지역(주방)이 실재하고, 사용자와
이미 합의한 동작 방식은 *"음영지역에서는 엣지에서 처리를 다 하고, 필요시
통신구역으로 이동"* 이다. 따라서:

**로컬 에이전트는 서버를 절대 기다리지 않는다.** 업로드 실패, 응답 지연, 서버
부재가 로봇 동작에 어떤 영향도 주면 안 된다. 서버는 **있으면 좋은 것**이지
동작 조건이 아니다.

### 절대 서버로 넘기지 않는 것

| 기능 | 이유 |
|---|---|
| **비상정지** | 하루를 들여 3개 버그를 잡은 기능이다. 네트워크를 경유시키면 실패 경로가 하나 더 생긴다 |
| **수동 조종** | 지연이 곧 사고다. 조종은 로봇과 직접 |
| **주행·회피·모터 제어** | 당연히 실시간 |
| **블랙박스 기록** | 통신이 끊긴 순간을 기록해야 하는데 그 기록을 통신으로 보낼 수는 없다 |

## 2. 역할 분담

### 로컬 에이전트 (로봇)

사용자와 직접 맞닿는 편의 기능 + 자율 동작. **서버 없이 완결된다.**

- 자율주행·매핑·복귀, 비상정지, 수동 조종
- 음성 상호작용의 **앞단**(웨이크워드, 발화 감지, 로컬 응답). 무거운 STT/TTS는
  서버로 보내되, **서버가 없으면 정해진 로컬 응답으로 축약**한다
- **최소 로컬 화면** — 통신이 끊겼을 때를 위한 상태 표시와 비상정지. 지금의
  대시보드 5개를 여기까지 줄인다
- 텔레메트리·가방·맵을 **로컬에 버퍼링**하고 기회적으로 업로드

⚠️ 대시보드 축소는 성능 문제이기도 하다. 오늘 프리즈의 유력한 방아쇠가 CPU
부하였고, 대시보드 5개는 SLAM·Nav2와 같은 코어를 쓴다.

### 서버 (관제탑)

모아야 가치가 생기는 것, 그리고 파이에 부담인 계산.

| 기능 | 왜 서버인가 |
|---|---|
| **통합 대시보드** | 기체가 늘면 로봇마다 접속할 수 없다. 로봇은 상태만 올리고 렌더링은 서버가 |
| **기체별 백업** | 유닛 설정·보정값·맵. SD가 죽어도 잃는 게 없어야 한다 |
| **맵 저장소와 공유** | 한 기체가 만든 맵을 다른 기체가 쓴다. 버전·이력 관리 포함 |
| **텔레메트리 축적과 비교** | **유닛 간 비교가 진짜 가치다.** 2호기만 복구동작이 많다면 소프트웨어가 아니라 그 개체의 기계 문제다 — 1대로는 절대 알 수 없다 |
| **성과물 보관** | 가방(주행 녹화), 맵, 품질 지표. 오늘 만든 것이 전부 여기 있어야 했다 |
| **재생 실험 harness** | `replay_slam.py` 같은 것. 파이에서 3배속도 버겁다. 서버면 여러 파라미터를 **병렬로** 돌려 비교할 수 있다 |
| **OTA 배포** | 버전 관리와 롤백 |
| **STT/TTS** | 파이에서 불가능 |

## 3. 데이터 흐름

```
로봇                                          서버
────────────────────────────────────────────────────────────────
[블랙박스] ─ 로컬 링버퍼 ─┐
[텔레메트리 요약]        ├─ 기회적 업로드 ──> [시계열 저장소]
[주행 가방]              │   (WiFi 좋을 때)      [기체 간 비교]
[맵 + 품질 지표]         ┘                       [통합 대시보드]
                                                       │
[유닛 설정/보정] <──── 백업 복원 ──────────────── [기체별 백업]
[맵] <──────────────── 공유 배포 ──────────────── [맵 저장소]
[애플리케이션] <────── OTA ────────────────────── [릴리스 채널]
```

### 업로드 규칙

1. **비동기·비차단.** 별도 프로세스. 실패해도 재시도 큐에 넣고 로봇은 계속 간다
2. **서버 확인 후에만 로컬 삭제.** 가방 29.5 MB/4분이라 카드가 금방 찬다.
   하지만 확인 없는 삭제는 성과물 유실이다
3. **요약 먼저, 원본 나중.** 텔레메트리 요약(작음)은 자주, 가방(큼)은 유휴 시간에
4. **쓰기 예산 안에서.** 로깅이 SD 수명을 깎는다 — 원시 데이터는 tmpfs, 요약만 카드에
   (`fleet_and_lifecycle.md` 6장)

## 4. 지금 순서 — 관제할 대상부터 있어야 한다

1호기 하나도 자율주행이 안 되는 상태에서 관제탑부터 지으면 **관제할 대상이 없는
관제탑**이 된다. 가치 순서로:

| 순서 | 할 일 | 왜 이 순서인가 |
|---|---|---|
| **1** | **성과물 업로드** — 맵, 가방, 품질 지표 | 기체 1대여도 즉시 가치. 오늘 만든 것들이 SD와 함께 사라질 수 있다 |
| **2** | **텔레메트리 업로드** | `blackbox_recorder.py`가 이미 로컬에 쌓는다. **전송 한 단계만** 붙이면 된다 |
| **3** | 서버 재생 실험 harness | 파이의 계산 병목 해소. 파라미터 탐색이 병렬로 가능해진다 |
| **4** | 로컬 대시보드 축소 + 서버 통합 대시보드 | CPU 회수. 단 **비상정지·수동조종은 로컬 유지** |
| **5** | 기체별 백업/복원 | 2호기 프로비저닝과 함께 (`fleet_and_lifecycle.md` 3장) |
| **6** | 맵 공유, OTA | 기체 2대 이상부터 의미 |

⚠️ 1~2번은 **서버가 아주 단순해도 된다.** 유닛 3대 규모에 카프카 같은 건 필요 없다.
HTTP 업로드 엔드포인트 + 파일 저장 + 정적 페이지면 충분하다. 과설계는 그 자체로 비용이다.

## 5. 열린 질문

- **서버를 어디에 두나** — 집 안 상시 가동 PC / NAS / 클라우드. 음영지역 이동
  전략을 생각하면 집 안이 자연스럽다. 다만 상시 가동 장비가 필요하다
- **인증** — 가정 내 폐쇄망 전제라면 최소한으로. 외부 노출 시엔 필수
- **로컬 화면을 어디까지 남기나** — 통신 두절 시 비상정지는 반드시 로컬. 그 외
  어디까지 서버로 옮길지는 실사용에서 정한다
