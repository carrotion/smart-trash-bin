## 2. 병목 재정의 — 문제가 이동했다

**국소(초 단위) 오도메트리는 이제 양호하다.** 동결 해결, 직진 정상, 회전 폐루프
추종 정상. 08-24 시점의 "메인 파이프라인이 조용히 끊긴다"는 문제는 끝났다.

**지배 오차는 장주기 요(방위) 드리프트다.** 두 성분이 실측으로 확인됨:
- 자이로 바이어스 방랑 ~3°/min (항목 4) — 세션이 길수록 선형 누적
- 회전 스케일 오차 × 큰 총회전량 (항목 5) — 많이 돌수록 누적

그리고 **SLAM이 이걸 흡수하지 못했다** — 루프클로저가 두 세션 모두 한 번도 안
걸렸다. `loop_search_maximum_distance: 3.0`은 "SLAM이 믿는 현재 위치" 기준
반경이라, 드리프트가 3m 상당을 넘은 뒤에는 실제로 같은 자리에 돌아와도 후보
탐색 자체가 안 된다.

⚠️ **기록해둘 조언 오류(Remi)**: 2차 매핑 전 "마지막에 시작점으로 크게 돌아오라"고
제안했는데 이는 위 메커니즘상 역효과였다(돌아올 때쯤엔 이미 탐색 반경 밖 +
그 사이 회전량만 증가). "작은 루프를 자주"가 이론상 맞지만 **이것도 아직
가설이다 — 아래 계획의 재생 실험으로 검증할 것.**

병진(거리) 오차는 부차적: 직진 시험·엔코더 정합 모두 정상, 08-24의 거리 스케일
가설도 ~2% 수준.

### 6.2 팩트체크 중 발견한 별도 버그 — 자이로 바이어스가 두 곳에서 따로 관리됨

`-0.00782`가 왜 아직도 라이브 파라미터에 남아있는지 추적하다가 리포트에
없던 문제를 발견:

- `diff_drive_node.py`는 **매 시작마다** 정지 상태 100샘플로 자이로 바이어스를
  새로 잰다(오늘 로그: -0.00113/+0.00367/+0.00287/+0.00618/-0.00410 rad/s로
  세션마다 다름). 하지만 이 값은 diff_drive_node **내부**(폐루프 제어,
  신뢰 안 하는 휠전용 `/odom`)에서만 쓰인다.
- `imu_publisher_node`는 **별개의 고정 상수** `gyro_bias_z`를 쓰는데, 이게
  `smart-trash-imu.service`에 `-0.00782`로 하드코딩돼 **2026-08-21 이후
  한 번도 안 바뀐 채** 있었다.
- **EKF(`ekf.yaml` `imu0: imu/data`)는 이 두 번째(고정) 값이 적용된 스트림만
  구독한다.** 즉 SLAM이 실제로 쓰는 요 추정치는 diff_drive_node의 매번-새로운
  재보정 혜택을 **전혀 못 받고 있었다.**
- 오늘 실측 잔차(고정값 대비 최대 ~0.006 rad/s)를 11분(675초) 세션에 그대로
  적분하면 이론상 수백 도까지 쌓일 수 있는 크기 — 오늘 두 매핑 세션의
  map→odom 보정(62.8°/-30.3°) 상당 부분을 이걸로 설명 가능. Davi의 "열드리프트
  85%" 주장보다 **이 구조적 버그 쪽이 훨씬 크고 확실한 기여자**로 보임.

### 6.3 수정 — imu_publisher_node에도 매 시작 자동 재보정 추가

`diff_drive_node`와 동일한 방식(정지 가정, N샘플 평균)을 `imu_publisher_node.py`에
이식. 새 파라미터 `gyro_bias_auto_calibrate`(기본 true), `gyro_bias_calib_samples`
(기본 100). 보정 대기 중엔 z=0.0 + covariance 상향(EKF가 그 구간을 안 믿게)으로
처리. `gyro_bias_z`(고정값)는 `auto_calibrate:=false`일 때의 비교/폴백용으로 유지.

**배포 및 즉시 검증**:
```
자이로 Z 자동 재보정 시작 — 정지 상태로 100샘플 대기
자이로 Z 자동 재보정 완료: -0.00691 rad/s (100샘플)
```
새 값(-0.00691)이 옛 고정값(-0.00782)과 근접하지만 다름 — 매번 다시 재는 게
실제로 작동함을 확인. diff_drive_node 잔차도 -0.00410으로 정상 갱신됨.

**아직 안 한 것**: 실제 주행/매핑으로 map→odom 보정량이 줄어드는지 검증 —
다음 매핑 세션에서 확인할 것 (판정 기준: 62.8°/-30.3° 대비 유의한 감소).
코드: `robot/src/smart_trash_sensors/smart_trash_sensors/imu_publisher_node.py`,
`tools/systemd/smart-trash-imu.service`.

## 7. 재매핑 재현 + 정밀 회전 시험 → 진짜 병목은 EKF 융합 (2026-08-29 저녁, ✅ 원인 확정·수정 완료 — 7.7절)

### 7.1 6절 수정 배포 후 재매핑 — 여전히 왜곡, 오히려 최악

새 IMU 재보정 적용 후 사용자가 거실/주방 직사각형 한 바퀴만 돌았는데
(다른 방은 갈 필요도 없다고 판단할 만큼 이미 확실했음) **map→odom yaw
보정 73.4°** — 오늘 세 번째 매핑 중 최악. 세션 길이는 243초로 앞의 두
번(675초, 340초)보다 훨씬 짧은데도 그래서, 시간당 왜곡 속도로 보면
가장 심각함(18.1°/분 vs 이전 5.4~5.6°/분). 루프클로저는 여전히 0건.

이 세션 총 절대회전량이 **1339°**(순회전은 +422°)로, "직사각형 한 바퀴"
치고 과하게 많음 — 스케일 오차 가설(자이로 배율이 틀려서 회전량에 비례해
오차가 쌓인다)이 이때 처음 제기됨.

### 7.2 정밀 회전 시험 (`gyro_scale_test.py`, 신규) — 결정적 시험

10바퀴(3600°, w=1.0rad/s, 62.83초) 회전을 명령하고 원시 자이로 적분 vs
EKF 융합 적분을 동시에 기록. **사용자가 육안으로 정확히 10바퀴(시작과 같은
방향)로 끝난 것을 확인** — 이게 이 시험의 진짜 정답지(3600°).

| 소스 | 결과 | 기대 대비 비율 |
|---|---|---|
| 명령(정답, 육안 확인) | 3600° | 100% |
| **원시 자이로 적분** | 3574.6° | **99.29%** ✅ 센서 정상 |
| **EKF 융합 적분** | 798.5° | **22.18%** 🔴 |

**스케일 오차 가설은 기각.** 원시 센서는 거의 완벽(0.71% 오차, 노이즈
수준) — 병목은 센서가 아니라 **EKF 융합 단계**에서 실제 회전의 5분의 4를
그냥 잃어버리고 있다는 것.

### 7.3 SLAM/CPU 경쟁 가설도 기각

SLAM·라이다를 완전히 내리고(diff_drive/EKF만 남김) 동일 시험 재실행:

| 조건 | EKF 융합 비율 |
|---|---|
| SLAM 켠 채 | 22.18% |
| **SLAM 끈 채** | **37.03%** (`gyro_scale_test_noslam.csv`) |

SLAM을 꺼도 여전히 심각하게 부족(37%) — CPU 경쟁이 있으면 악화는 되지만
(37%→22%) **유일한 원인이 아니다.** SLAM 없는 "가장 깨끗한" 조건에서도
EKF는 실제 회전의 1/3도 못 잡는다.

### 7.4 실시간 각속도 직접 대조 — EKF가 새 측정을 거의 안 믿는 것처럼 보임

`/imu/data`(원시, 이미 자동재보정 적용됨)와 `/odometry/filtered`의
`twist.twist.angular.z`를 나란히 실시간 관찰(정상 회전 중):

```
gyro_z: +0.7 ~ +1.2 rad/s (노이즈 있지만 명령 1.0 rad/s 주변에서 정상 요동)
ekf_angular_z: +0.333 ~ +0.340 (거의 고정, 거의 안 움직임)
```

**EKF의 융합 각속도 추정치가 실제값의 1/3 근처에서 거의 얼어붙어 있다.**
매 사이클 새 자이로 측정이 들어오는데도 필터가 그걸 거의 반영하지 않는
것처럼 보임 — 정상적인 칼만 필터라면 지속적으로 정확한(노이즈만 있는)
측정을 몇 초 이상 받으면 그 근처로 수렴해야 하는데 그렇지 않음.

### 7.5 시도한 수정 — process_noise_covariance 상향, 오히려 악화 (⚠️ 되돌림)

`robot_localization`의 `ekf.yaml` 예제 자체 주석에 "회전 중 이 현상이
흔하고, 해당 변수(vyaw)의 `process_noise_covariance`를 올리면 완화된다"고
명시돼 있고, 우리 `ekf.yaml`엔 이 항목이 아예 없어(패키지 기본값 사용,
vyaw 기본 0.02) 가설과 정황이 맞아 vyaw만 1.5로 크게 올려 실험함.

**결과: 오히려 더 나빠짐.** 재시험한 실시간 각속도가 `-0.045 ~ -0.048`
(원시 자이로는 여전히 +0.8~+1.2)로, 이전(+0.333, 최소 부호는 맞았음)보다
**부호까지 반대인 더 나쁜 고정값**으로 수렴함. 단순 파라미터 하나 올리는
수준으로 고쳐지는 문제가 아니라는 뜻 — **설정을 되돌림(커밋 안 함)**.

⚠️ **다음에 이 문제를 다시 볼 사람에게**: `process_noise_covariance`의
vyaw만 올리는 시도는 이미 해봤고 악화됐다. 같은 걸 반복하지 말 것.
의심 후보(미검증):
- `two_d_mode: true`가 vyaw 처리와 예상 밖으로 상호작용할 가능성
- `imu0_config`의 인덱스가 실제로는 문서와 다르게 해석되고 있을 가능성
  (예: yaw(5번)와 vyaw(11번) 혼동 — 코드가 아니라 robot_localization
  내부 규약을 직접 재확인할 것)
- `initial_estimate_covariance`(우리 파일엔 이것도 미설정, 패키지 기본값)가
  수렴을 막고 있을 가능성
- 아주 단순한 최소 구성(odom0 없이 imu0만, 다른 파라미터 전부 기본값)으로
  격리해서 vyaw 융합 자체가 근본적으로 되는지부터 재확인
- `robot_localization` jazzy 버전 자체의 알려진 이슈 여부 (GitHub 이슈 검색)

### 7.6 현재 상태 (세션 종료 시점)

- `ekf.yaml`은 원래 커밋 상태로 **되돌려짐**(패키지 기본 process noise 사용,
  즉 22~37% 융합 문제가 있는 상태 그대로).
- `imu_publisher_node`의 자동 재보정(6절)은 그대로 유지 — 이건 실제로
  작동하고(사소하지만) 방향이 옳은 개선이라 되돌릴 이유 없음.
- SLAM/라이다는 이 시험을 위해 내려간 채로 세션 종료.
- **다음 세션 최우선**: 이 EKF 융합 손실 문제. M1(해결), 자이로 바이어스
  이중관리(해결)보다 훨씬 큰 영향력(22~37% 미만 캡처)을 가진, 오늘 밝혀진
  진짜 지배 오차 원인. `docs/pc_tasks.md`에도 Resie용 후속 조사 항목으로
  올릴 것(로그: `docs/calibration/gyro_scale_test*.csv`).

### 7.7 근본원인 확정 + 수정 완료 — `base_link→imu_link` TF가 아예 없었다

7.5절의 되돌린 시도(process_noise_covariance) 이후, `robot_localization`의
`debug: true` 옵션으로 실제 내부 처리 로그를 직접 열어봄(`ekf_node`를
`-p debug:=true -p debug_out_file:=...`로 수동 실행, 5초 회전 캡처).

**결정적 증거**: `processMeasurement (odom0_pose)`와 `(odom0_twist)`는
5초간 각 1302회 호출됐는데, **imu0 관련 `processMeasurement`는 0회.**
대신 반복되는 문구를 발견: `Could not transform measurement into
base_link. Ignoring...`

**원인**: `imu_publisher_node`가 `frame_id: imu_link`로 `/imu/data`를
발행하는데, **`base_link → imu_link` 정적 TF가 시스템 어디에도 없었다**
(`ros2 run tf2_ros tf2_echo base_link imu_link` → "frame does not exist").
`hardware_inventory.md`엔 "vyaw만 쓰니까 장착 위치 무관 → TF 불필요"라고
**잘못 기록**돼 있었음 — 물리적으로는 맞는 추론이지만, `robot_localization`은
어떤 필드를 쓰든 **메시지 프레임→타깃 프레임 변환을 먼저 시도**하고 TF가
없으면 **메시지 전체를 버린다.** 그 결과 diff_drive_node의 채널별
캘리브레이션도, 오늘 고친 자동 바이어스 재보정도, M1 케이블 고정도 —
전부 옳은 조치였지만 **EKF엔 애초에 IMU 데이터가 한 번도 안 들어가고
있었으니** 지도 왜곡에 영향을 줄 수가 없었다.

**수정**: `smart-trash-imu-tf.service` 신설 — `base_link→imu_link` 정적 TF
상시 발행 (x=+0.105 y=0 z=0.090, `hardware_inventory.md` IMU 장착 기하와
일치). 재시작 후 즉시 실시간 대조로 확인:

```
gyro_z:        +0.82 ~ +1.05 rad/s
ekf_angular_z: +0.90 ~ +1.08 rad/s   (수정 전: 고정 +0.33, 실패한 시도 후엔 -0.045)
```

**두 값이 이제 실제로 서로 따라간다.** `hardware_inventory.md`도 정정하고
교훈("필드가 위치 무관이어도 미들웨어는 메시지 단위로 먼저 거를 수 있다 —
추론만으로 TF 생략을 단정하지 말 것")을 남겨둠.

**아직 안 한 것**: 이 수정으로 실제 매핑 세션의 map→odom 왜곡이 실제로
줄어드는지 검증 — 다음 매핑 시험에서 확인. 판정 기준: 62.8°/-30.3°/73.4°
대비 유의한 감소(루프클로저 없이도 몇 도 이내로 좁혀지길 기대).

### 7.8 실전 검증 완료 — 사용자 확인 "거의 완벽" ✅

수정 후 첫 실제 매핑(10분, `manual_mapping4_1706.csv`)에서:

- **M1 4채널 동기화 정지 0건** (10분 전체).
- **맵이 처음으로 깨끗한 직각 방들로 그려짐** — 이전 세 번(62.8°/-30.3°/73.4°
  왜곡, 방이 회전되거나 이중으로 겹쳐 보이던 것)과 달리 방·복도 경계가
  또렷하고 벽이 서로 어긋나지 않음. 사용자 직접 확인: "대박 거의 완벽해."
- ⚠️ **map→odom yaw 자체는 여전히 크다(-157.99°)** — 그런데 이건 문제가
  아니었다. 이 값은 "odom 프레임의 세션 시작 방향"과 "map 프레임의 절대
  방향" 사이 차이일 뿐이라 애초에 임의값이고, 세션마다 로봇이 EKF/diff-drive를
  재시작한 시점에 어느 쪽을 보고 있었는지에 좌우된다 — **작을 이유가 없다.**
  62.8°/-30.3°/73.4°를 "왜곡의 크기"로 해석했던 것 자체가 부정확한 지표였다:
  진짜 신호는 이 절대값이 아니라 **맵 자체의 내부 일관성**(방이 서로 직각을
  이루는지, 벽이 겹치는지)이었다. 다음부터는 이 숫자 하나로 판단하지 말고
  맵 이미지를 직접 볼 것 — `docs/pc_tasks.md` task 11-a 하네스 같은 자동
  평가 지표를 쓸 때도 "map→odom yaw 절대값"이 아니라 "루프클로저 성공 여부
  + 방 직각도"를 기준으로 삼아야 함(이 문서 4절 "평가 지표 고정" 갱신 필요).

**결론**: `base_link→imu_link` TF 부재가 오늘 하루 종일 겪은 매핑 왜곡의
진짜 근본원인이었음이 실전에서 확정됨. Layer 0(자기위치 인식) 이슈는
사실상 종료 — 남은 건 여전히 루프클로저가 0건이라는 점(4절 계획대로
`docs/pc_tasks.md` task 11-a 하네스로 이제 진짜 필요한 실물 bag을 얹어
후속 튜닝할 것) 정도.

## 8. Layer 2 첫 실물 자율탐색 시도 — 2회 충돌, 가는 다리류 감지 한계 의심 (2026-08-29 저녁)

Layer 0/1이 해결된 김에 그동안 시뮬레이션에서만 튜닝했던 explore_lite를
처음으로 실물에 올려봄(`autonomous_mapping.launch.py`, 이미 실물 튜닝된
`explore_params.yaml`/`nav2_params.yaml` 사용 — 패치 적용 확인 완료).

### 8.1 1차 시도 — 식탁 다리 충돌

- 시작 직후 explore_lite가 정상적으로 목표를 보내고 주행 시작(Nav2 lifecycle
  전부 정상 activate 확인).
- 주행 약 57초 지점(`t=165.28`)에 `Failed to make progress` → 로컬
  코스트맵 전체 초기화(`Received request to clear entirely the
  local_costmap`) → 직후 재출발. 사용자 보고 타이밍("거실 중앙→주방 지그재그
  이동 중 충돌")과 대략 일치.
- **`controller_server`의 제어 루프가 목표 10Hz 대비 6.1~7.3Hz로 저하**
  (`Control loop missed its desired rate` 경고 2회 확인) — SLAM+Nav2+탐색을
  동시 구동하는 부하 + 이번 세션에서 새로 띄운 `foxglove_bridge`(다수 토픽
  실시간 직렬화)가 유력한 원인으로 추정, 실측 검증 전.
- **다친 사람/파손 없음.**
- 조치: foxglove_bridge 중지 후 재시도. (속도 자체는 `max_vel_x=0.04m/s`로
  8/17~8/22 동안 이미 0.3→0.15→0.08→0.04로 여러 차례 낮춰진 하한선 —
  "속도를 더 낮춘다"는 이미 소진된 레버였음, 착각해서 처음에 잘못 제안함.)

### 8.2 2차 시도 — 의자 다리 충돌, 다른 근본 가설로 이동

foxglove 중지 후 재시도했으나 **또 충돌**(의자 다리) — CPU/foxglove 가설이
1차 문제를 설명하는 전부는 아니었음을 시사. 두 충돌 모두 **가늘고 낮은
다리류(식탁/의자)**라는 공통점에 주목해 가설을 전환.

**새 가설(미검증) — 자기필터의 근접 사각지대**: `scan_self_filter`는
`base_link` 중심 ±0.105m 폴리곤 안의 점을 "내 몸체"로 보고 지운다
(2026-08-17 도입, `config/scan_self_filter.yaml`). 이 필터는 순수
기하학적 거리 판정이라, **실제 외부 장애물이라도 로봇에 10.5cm 이내로
가까워지면 자기 구조물과 구분 없이 같이 지워진다.** 다리류는 폭이 좁아
로봇이 아주 가깝게 붙어야 지날 수 있는지 판단이 서는 경우가 많은데,
바로 그 근접 구간에서 필터가 오히려 그 장애물을 코스트맵에서 지워버릴
가능성이 있음.

**확인 시도**: 충돌 직후 현재 위치에서 `/scan_raw` 스냅샷 확인 — 0.079~
0.080m 거리 클러스터(52~69°)가 나왔으나, 이는 2026-08-19 실측 기록의
자기 구조물 시그니처(54~68°, 0.080m, 표준편차 0.0001~0.0005)와 완전히
일치 — **로봇 자기 몸체이지 의자 다리가 아니었음.** 즉 이 스냅샷만으로는
가설을 확증도 반증도 못 함(충돌 후라 다리가 스캔 경로에서 벗어났을 가능성).

**⚠️ 미해결, 다음 세션 최우선 후보**: 가설을 제대로 검증하려면 로봇을
얇은 다리에 **손으로 천천히** 접근시키며 `/scan_raw`(필터 전)와
`/scan`(필터 후)을 동시에 실시간 대조 — 접근 중 어느 거리에서 `/scan`에서
그 점이 사라지는지 직접 관찰. 확인되면 대응 후보:
- 자기필터 폴리곤을 실제 footprint(±0.11)에 더 타이트하게 맞춰 여유를 줄임
  (다만 진짜 자기 구조물 오탐 위험과 트레이드오프)
- 거리 기반 필터 대신 반사 신호의 **일관성**(여러 프레임에 걸쳐 항상 같은
  거리로 나오면 자기 구조물, 변하면 외부 장애물)으로 구분하는 방식 검토
- ToF(VL53L5CX, `hardware_inventory.md` 도입 예정 2순위)로 근접 구간을
  라이다와 별도로 보강 — 원래 목적(높이 사각지대)과 다르지만 근접 사각지대
  에도 도움 될 수 있음

### 8.3 오늘 부수 발견 — `mapping_cleanup.py`가 `smart-trash-imu-tf`를 오살(誤殺)

세션 정리(`static_transform_publisher` 이름 매칭)가 오늘 신설한 상시 서비스
`smart-trash-imu-tf.service`까지 같이 죽이고 있었음 — 2차 자율주행 launch
직후 발견(`systemctl status`로 "restart counter is at 3" + systemd 재시작
버스트 한도로 자동복구 안 됨 확인). **자율주행 도중 EKF가 다시 IMU를
못 쓰는 상태로 몇 분간 돌고 있었다는 뜻** — 다행히 충돌 원인과는 무관해
보이나(로컬 코스트맵 기반 충돌 회피는 절대위치 정확도와 별개), 오늘 고친
핵심 수정이 조용히 무력화될 뻔했음. **수정 완료**: `mapping_cleanup.py`가
`static_transform_publisher` 중 인자에 `imu_link`가 포함된 것은 제외하도록
패치(`find_session_processes()`). 재검증: imu-tf는 세션 프로세스 목록에서
빠지고, 매핑용 base_laser TF는 여전히 정상 정리됨.

### 8.4 (8.5절로 이어짐 — 아래 M3 발견 이후 재해석)

## 9. 자기필터 근접시험 중 M3 엔코더 커넥터 단선 발견·수리 + 속도 캘리브레이션 전면 붕괴 확인 (2026-08-29 밤)

8.2절 가설(자기필터 근접 사각지대) 검증을 위해 도크에서 정밀 접근 시험을
준비하던 중, 채널별 이동거리 대조에서 **M3(오른쪽 뒤) 엔코더가 완전히
죽어있는 것**을 발견 — 별개의, 더 시급한 문제였음.

### 9.1 M3 엔코더 완전 정지 발견 → 커넥터 재체결로 해결

`0.2m/s×2초`(기대 40cm) 시험에서 채널별 카운트: M1 -2017 / M2 -2023 /
**M3 0** / M4 -2012 — M3만 정확히 0. 반복 재현(2회) 후 사용자가 M3 엔코더
커넥터를 직접 뽑아 확인 → **헐거운 것 발견, 재체결**. 이후 동일 시험에서
M3 -3395(M1 -3383/M2 -3421/M4 -3494와 3% 이내 일치) — **완전히 정상화**.

⚠️ 이동 중 실제로 로봇이 헛디딜 만큼 세게 움직인 부수 사고 1건 발생(4개
연속 충돌 중 하나, 무인 무피해) — 원인은 아래 9.2절.

### 9.2 "명령보다 훨씬 멀리 간다" — 이중 원인 확정 (실측 완료)

M3 수리 직후부터 모든 거리 시험이 명령보다 훨씬 많이 이동하는 현상이
반복돼 체계적으로 조사(사용자 제안 — 속도/시간을 각각 바꿔가며 비교,
그리고 관성 코스팅 가설 제안). `/cmd_vel`을 직접 실시간 기록해서 **외부
발행자 간섭은 완전히 배제**(수천 건 메시지 전부 명령값과 정확히 일치,
motor_dashboard/map_dashboard_bridge 등 다른 발행자 개입 0건).

**실측 표** (엔코더 계산, 줄자 실측과 3~4% 이내로 일치 확인됨):

| 명령 | 시간 | 기대거리 | 실제거리 | 배율 |
|---|---|---|---|---|
| 0.1m/s | 2s | 20cm | 85cm(실측 100cm) | 4.3~5배 |
| 0.1m/s | 3s | 30cm | 116cm(실측 127cm) | 3.9~4.2배 |
| 0.2m/s | 3s | 60cm | 136cm(실측 140cm) | 2.3배 |

**원인 ① — 정속 구간 자체가 명령보다 약 2~2.7배 빠름.** `_speed_to_pwm()`이
낮은 속도를 `min_pwm=120` 데드존 문턱으로 강제 상향시키는데, 여기에
`motor_pwm_offset_m3=+240`(2026-08-20에 M3 기계적 드래그 보정용으로 잡은
값)까지 무조건 더해져 평균 PWM이 의도치보다 49% 이상 부풀려짐. 오늘 M1
케이블·M3 커넥터를 고치면서 **실제 마찰이 줄어든 상태**인데 예전 마찰
기준으로 잡은 오프셋·데드존이 그대로 남아 있어 문턱 근처 비선형성까지
겹쳐 배율이 낮은 속도일수록 더 커짐(0.1m/s가 0.2m/s보다 배율 큼).

**원인 ② — 정지 명령 후 관성 코스팅.** 소프트웨어 가속램프는 감속에는
안 걸림(코드 확인: `target_v=0`이면 즉시 추종, 램프 없음) — 그런데도
0.2m/s 정속(1.5초) 직후 정지 명령을 보내고 나서 **0.65~0.8초에 걸쳐
24cm를 추가로 더 굴러감**(실측, 줄자 대조 83.6cm 계산 vs 80cm 실측 ±4%).
**순수 물리적 관성**이며, 오늘 마찰이 줄어 코스팅 거리도 예전보다
길어졌을 것으로 추정. 짧은 거리/저속 명령일수록 이 고정폭 코스팅이
차지하는 비중이 커서 배율이 더 커 보이는 이유를 정확히 설명함(사용자가
직접 제안한 가설, 실측으로 확증).

### 9.3 결론 및 다음 조치

두 원인 다 "로봇이 고장났다"가 아니라 **오늘 두 하드웨어 수리(M1 케이블,
M3 커넥터)로 마찰이 실제로 줄어서, 그 마찰을 전제로 잡혀있던 모든
저속 PWM 캘리브레이션(데드존 `min_pwm`, 채널별 오프셋, `max_wheel_speed`
스케일)이 낡아버린 것** — 물리적으로는 개선인데 소프트웨어 캘리브레이션이
못 따라간 상태. `straight_check.py`/`motor_channel_test.py`로 데드존·
오프셋·속도스케일 전면 재측정이 다음 최우선 과제. 코스팅(관성) 자체는
캘리브레이션으로 없앨 수 없고, 빠른 정지가 중요한 상황(장애물 근접 등)
에선 짧은 역방향 브레이크 펄스 같은 능동 제동을 고려할 것.

## 10. 오늘 종합 결론

Layer 0(자기위치) 완전 해결 + Layer 1(매핑) 실전 검증 완료. Layer 2
(자율탐색) 첫 실물 시도는 2회 충돌로 새 한계(자기필터 근접 사각지대,
미확증) 발견. 그 가설을 검증하려던 정밀 접근 시험 도중 **M3 엔코더
커넥터 단선을 발견·수리**했고, 그 여파로 드러난 **저속 PWM 캘리브레이션
전면 붕괴**(데드존/오프셋/코스팅)까지 규명·실측 완료. 오늘 하루에 걸쳐
Layer 0의 세 겹 원인(M1 커넥터, `base_link→imu_link` TF, M3 커넥터)이
전부 밝혀지고 고쳐졌다는 게 가장 큰 그림 — 다음 세션은 (1) 저속 PWM
재캘리브레이션, (2) 자기필터 근접 사각지대 가설 검증, (3) Layer 2
재시도 순으로.

## 11. 코스팅 실측 기반 정밀거리 이동 도구 개발·검증 (2026-08-29 밤)

9.2절에서 확인된 두 원인(정속 구간 배율, 정지 후 관성 코스팅)을 실제로
활용 가능한 도구로 만듦 — 시간×속도 예측(개루프) 대신 **엔코더로 실시간
이동거리·속도를 재고, "지금 멈추면 코스팅으로 얼마나 더 갈지"를 매 순간
예측해서 그 합이 목표에 닿는 순간 구동을 끊는** 폐루프 방식.

### 11.1 코스팅 모델 데이터 수집·피팅 (사용자 주도)

`tools/coast_sweep.py`(신규)로 속도 0.1~0.8m/s 구간에서 16회 측정
(`docs/calibration/coast_sweep.csv`). 사용자가 직접 제안한 실험설계
(속도·시간을 각각 바꿔가며 배율의 정체 파악) 및 후속 모델 검토 요청
(선형/제곱/거듭제곱/지수 비교)에 따라 여러 함수형을 피팅:

| 모델 | RMSE(11~13개 기준) |
|---|---|
| 제곱(등감속 물리모델) v² | 12.6cm — 확실히 기각 |
| 거듭제곱 v^0.467 | 7.2cm |
| 포화/성장 지수 | 6.8~7.2cm (파라미터가 탐색범위 끝에 붙어 사실상 선형 수렴) |
| **선형(원점통과) v** | **6.9cm — 채택** |
| 선형+절편 | 6.3cm(근소 우위지만 물리적으로 v=0 코스팅이 0이 아닌 게 부자연스러워 기각) |

**결론**: 등감속을 가정한 "당연해 보이는" 제곱모델이 제일 안 맞았고,
지수/거듭제곱도 선형보다 나은 설명력을 못 보여줌 — 추가 차원 없이
`coast = 0.53 × v`(원점통과 선형)로 확정. RMSE 6~7cm은 남은 노이즈로,
배터리 전압·바닥 마찰 변동 등 미포함 변수가 있을 수 있음(추가 조사 여지).

### 11.2 `tools/precise_move.py` — 실측 검증 + 치명적 버그 발견·수정

⚠️ 표는 **목표 대비 실제(줄자) 오차**를 기준으로 본다 — 초반에 "엔코더
계산값과 줄자 실측값이 서로 비슷하다"는 것을 "목표를 잘 맞췄다"로
잘못 전달한 적이 있었음(사용자 지적으로 정정, 2026-08-29 밤). 엔코더-줄자
일치는 "측정 도구 자체가 정확하다"는 뜻일 뿐, 목표 달성 여부와는 별개.

목표거리 3건 실물 시험(줄자 대조):

| 목표 | 줄자 실측 | 오차 | 비고 |
|---|---|---|---|
| 50cm | ~50cm(살짝 못미침) | ~1% | |
| 100cm | 90cm | ~10% | |
| 200cm | 188cm | ~6% | 아래 버그 수정 후 재시행 |

**실용 정밀도는 대략 ±6~10%**(코스팅 모델 RMSE와 대략 일치) — 개루프
시절의 2~5배 오차와는 차원이 다르지만 완벽하진 않음.

**🔴 치명적 버그 발견·수정 (200cm 1차 시도에서)**: 목표 200cm를 줬는데
`v_est=23.979m/s`(물리적으로 불가능한 값)가 찍히며 **37cm만 가고 조기
정지**. 원인: 엔코더는 diff_drive_node 폴링 주기(~60~80ms)마다만 갱신
되는데 이 스크립트의 속도추정 루프는 ~20ms마다 도니, 시행 초반
`hist`(속도추정용 최근 0.3초 샘플 창)가 아직 짧을 때 두 샘플의 시간차가
1e-3(반올림 방지용 최소값) 근처까지 내려가면서 나눗셈이 폭발함 —
코스팅 예측이 12.8m로 튀어 "이미 목표 도달"로 오판했다.

**이번엔 조기정지(목표 미달)로 끝났지만, 반대 부호로 튀었으면 과주행
(충돌 위험)이 될 수 있었다** — 실제로 벌어질 수 있었던 안전 버그.
수정: 속도추정 시간창이 **0.15초 미만이면 그 추정을 신뢰하지 않고
v_est=0으로 처리**(구동을 계속 유지하는 쪽이 안전 — 코스팅 보정 없이
그냥 목표에 못 미쳐 멈추는 방향이 과주행보다 안전), 추가로 물리적
상한(2.0m/s)으로 재차 클램프. 수정 후 재시행: 목표 200cm → 줄자 실측
188cm(6% 오차, 정상 범위) — 버그 완전히 해소됨.

**교훈**: 폐루프 안전장치(엔코더 실시간 감시)를 만들 때도 그 안의
**추정치 자체가 극단값으로 발산할 수 있는 경로**(작은 분모, 초기
데이터 부족 등)를 항상 클램프/최소 표본 조건으로 막아야 한다 — "실시간
피드백이니까 안전하다"고 방심하면 안 됨.

좌우 드리프트 보정(11.3절)과 코스팅 데이터 추가 수집(노이즈 원인 조사)이
정밀도를 더 좁힐 다음 과제.

### 11.3 부수 발견 — 왼쪽 드리프트 (~3~4%, 미해결)

이 시험들 도중 반복적으로 **좌측 대비 우측이 조금 더 많이 이동**(직진
폐루프가 적용된 상태에서도 전체 거리의 3~4%)하는 경향을 확인 —
로봇은 이 방향으로 살짝 왼쪽으로 휨. 오늘 M3 수리로 마찰이 바뀌면서
`turn_kp`/`turn_ki`(2026-08-20 캘리브레이션, 그 이후 하드웨어 변경 없이
유지되던 값)도 낡았을 가능성. 저속 PWM 재캘리브레이션(9.3절)에 이 항목도
포함할 것. `tools/coast_sweep.py`가 매 시행 좌우 이동량을 같이 기록하므로
추가 데이터 없이도 기존 `coast_sweep.csv` 로그만으론 부족 — 별도 좌우
드리프트 전용 로그가 필요하면 신규 도구 검토.
