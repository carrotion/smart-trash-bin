# 개인 프로젝트 기록: AI 협업으로 진행한 자율주행 로봇 개발

> 취업 소개자료·면접 활용을 위한 사실 정리. 수치는 저장소의 실측 기록에서 인용.
> 기간 2026-07-30 ~ 2026-08-20 (약 3주), 커밋 132건.

## 1. 프로젝트 개요와 당초 계획

### 목표

가정용 "스마트 쓰레기통" 로봇. 집 안을 자율 주행하며 지도를 만들고, 호출하면
이동하고, 봉투 교체 시점을 감지해 알린다.

### 초기 계획 (8주 Phase 0)

| 주차 | 목표 |
|---|---|
| 1 | ROS 2 워크스페이스 구성, IMU 연결 |
| 2 | 부품 수령, 전원부 배선/조립 |
| 3 | LiDAR + SLAM 매핑 검증, diff-drive 노드 |
| 4 | EKF 센서 융합, Nav2 기본 이동, ToF 장애물 감지 |
| 5~8 | 2호기 제작, 음성 파이프라인, 다중 로봇 협조 |

### 실제 진행

3주차까지의 계획 항목은 대부분 달성했으나, **Week 3~4에 예정된 "SLAM 매핑 검증"과
"Nav2 기본 이동"에서 예상보다 훨씬 많은 시간을 썼다.** 원인은 소프트웨어가 아니라
**기구·전원·배선 쪽 물리 문제**였고, 이것이 이 프로젝트의 실질적인 내용이 되었다.

## 2. AI를 활용한 개발 환경 구성

### 구성 방식

로봇(Raspberry Pi)에서 **AI 에이전트를 직접 실행**하는 형태로 구성했다.
원격 개발 PC에서 코드를 짜서 로봇에 배포하는 방식이 아니라, **AI가 로봇 위에서
직접 명령을 실행하고 센서 값을 읽고 결과를 보는** 구조다.

이 선택이 만든 차이:

- **측정과 수정의 왕복 시간이 사라졌다.** 파라미터를 바꾸고 → 빌드하고 → 측정하고
  → 다시 바꾸는 사이클이 한 대화 안에서 끝난다.
- **실측 없이 추정하는 일이 줄었다.** "이 값이 얼마일 것 같다"가 아니라 그 자리에서
  재볼 수 있다.

### 재현성을 위한 장치

프로젝트 중반부터 다음을 도입했다. 모두 **같은 실수를 반복하면서** 필요성을 깨닫고
만든 것이다.

| 장치 | 도입 이유 |
|---|---|
| `CLAUDE.md` (환경 메모, 46개 절) | AI는 세션이 바뀌면 대화를 기억하지 못한다. 저장소에 적힌 것만 남는다 |
| `docs/hardware_inventory.md` | 부품 정보가 3개 문서에 흩어져 전부 낡아 있었고, 그 때문에 잘못된 조언이 나왔다 |
| `docs/calibration/*.json` | 측정값을 **조건(날짜·배터리 전압·치수)과 함께** 보존. 조건 없는 측정은 다음 측정과 비교가 불가능하다 |
| 32개 진단 도구 (6,133줄) | 같은 측정을 즉석 스크립트로 반복하니 결과 형식이 달라 비교가 안 됐다 |
| rosbag 녹화·재생 환경 | 알고리즘 검증을 실물 로봇으로 하다가 벽에 밀어넣었다 |

### 실험 도구 예시

- `motor_channel_test.py` — 모터 4채널을 하나씩만 구동해 죽은 채널을 찾는다.
  안전 수칙(정지 확인 후 진행, 예외 시 정지 명령 3회 반복)을 코드에 내장했다.
- `rotation_calibrate.py` — 폐루프를 끄고 개루프 PWM–각속도 특성을 측정. 종료 시
  원래 게인으로 자동 복원.
- `lidar_occlusion.py` / `lidar_occlusion_plot.py` — 라이다 자기 차폐를 각도별로
  측정하고 위에서 본 그림으로 출력.
- `replay_slam.py` — 녹화한 주행을 재생하며 SLAM 파라미터만 바꿔 비교.
- `map_quality.py` — 맵의 벽 방향 정렬도를 수치화(실내는 직각 구조이므로 벽 방향이
  몇 개 축에 몰려야 정상).

## 3. AI 협업의 효과

### 3.1 물리 원리를 계산으로 좁혀 실험 횟수를 줄였다

**사례: 회전 마찰과 축간거리**

스키드 스티어는 회전 시 바퀴가 옆으로 긁힌다. 그 저항 토크는

    M_scrub = μ · m · g · L / 2      (L = 축간거리)

즉 **윤거(track)가 아니라 축간거리에만 비례**한다. 축 방향 속도 성분은 바퀴가
굴러서 흡수하기 때문이다. 이 관계를 근거로 축간거리를 125mm → 108mm로 줄였고,
계산상 마찰 13.6% 감소를 예상했다.

**실측 결과는 예상보다 훨씬 컸다.**

| PWM | 변경 전 | 변경 후 | 증가 |
|---|---|---|---|
| 250 | 0.187 rad/s | 0.766 rad/s | **+309%** |
| 400 | 0.530 | 1.500 | +183% |
| 500 | 0.773 | 1.879 | +143% |
| 데드존 | PWM 230 | **PWM 49** | |

**13.6%가 3배로 나타난 이유**: 모터는 토크-속도 곡선에서 부하와 균형점을 찾는다.
변경 전에는 구동 토크가 스크럽 마찰을 간신히 넘는 **스톨 근처**에서 동작하고
있었다. 마찰이 조금 줄자 동작점이 곡선 위로 크게 올라갔다. 낮은 PWM일수록 개선폭이
큰 것도 이 설명과 일치한다.

이 해석이 없었다면 "왜 예상의 20배가 나왔지?"에서 멈추거나, 측정 오류로 의심하고
시간을 더 썼을 것이다.

### 3.2 실험 설계로 원인을 분리했다

**사례: 모터 한 채널이 22% 부족한 원인 규명**

세 가지 가설이 가능했다. 그런데 **각 가설은 전류에 따라 서로 다른 흔적을 남긴다.**

| 가설 | 예상 흔적 |
|---|---|
| 접촉 저항 (I × R 강하) | 전류 커질수록 부족분 **증가** |
| 약한 모터 (낮은 Kv) | 부족분의 **비율**이 일정 |
| 기계적 드래그 (일정한 저항 토크) | 부족분의 **절대량**이 일정 |

PWM을 200/300/450/600으로 훑어 측정:

    PWM        200    300    450    600
    부족(절대)  1005   1006   1031    969   <- 일정
    부족(비율) 25.6%  23.2%  20.8%  17.5%  <- 감소

**절대량이 일정 → 기계적 드래그로 확정.** 그리고 이 결과가 **보정 방식까지 정했다** —
일정한 저항 토크이므로 비율(gain)로 곱하면 저속에서 모자라고 고속에서 과해진다.
**PWM 오프셋(덧셈)**으로 보정해야 한다.

같은 결론이 독립적인 관찰로도 확인됐다. 사용자가 "그 바퀴만 관성이 부족한 것처럼
빨리 멈춘다"고 했는데, **같은 마찰이 구동 중에는 속도를 깎고 전원을 끊으면 더 빨리
세운다.** 두 현상이 하나의 원인을 가리켰다.

### 3.3 제어 이론을 실측에 연결했다

피드포워드 모델을 고쳤더니 오히려 진동이 생겼다. 원인은 **루프 이득**이었다.

    PWM->각속도 기울기  0.00234 (변경 전) -> 0.00412 (변경 후) = 1.76배 민감

플랜트가 1.76배 민감해지면 같은 게인에서 루프 이득도 1.76배가 된다.
게인을 1.76으로 나눈 값(142)이 실측 최적점(140)과 거의 일치했다.

| 게인 (kp/ki) | 추종 오차 | 각속도 표준편차 |
|---|---|---|
| 250 / 400 (기존) | 44% | 0.391 (진동) |
| **140 / 220** | **2%** | **0.074** |

**교훈**: 피드포워드를 바꾸면 게인도 반드시 재튜닝해야 한다. 둘은 독립이 아니다.

### 3.4 AI가 없었다면 겪었을 것

| 항목 | 예상 소요 |
|---|---|
| ROS 2 / Nav2 / SLAM Toolbox 파라미터 체계 학습 | 수 주 |
| 스키드 스티어 슬립 모델과 EKF 융합 설계 | 수 주 |
| 32개 진단 도구 작성 (6,133줄) | 상당 기간 |
| 커널 로그·DDS·udev 등 시스템 계층 문제 해결 | 개별 사안마다 며칠 |

다만 **아래 5장에서 서술하듯, AI가 만든 오류를 걸러내는 데도 상당한 시간이 들었다.**
순수한 시간 절약으로만 보면 과대평가가 된다.

## 4. 시련과 문제 해결

### 4.1 전원 차단 3회 — 원인은 배터리 위조품

3주 중 하루에만 전원이 3회 나갔다. 처음에는 소프트웨어 부하나 발열을 의심했다.

**실측으로 원인을 특정했다.**

| 측정 | 값 | 해석 |
|---|---|---|
| 충전기 무부하 출력 | **13.2V** | 3S 리튬 만충은 12.6V. 이 값은 납축전지 플로트 전압 |
| "완충" 표시 후 팩 전압 | **11.9V** (셀당 3.97V) | 만충(4.2V) 근처도 아니다 |
| 충전 중 단자 전압 | 11.9V (변화 없음) | **전류가 안 흐른다 = BMS가 차단한 상태** |

**충전기의 완충 신호는 "전류가 멈췄다"는 뜻이다.** 정상 팩이라면 전류가 멈추는 이유는
셀이 다 찼기 때문인데, 이 팩은 80%도 안 된 상태였다. 즉 **셀 하나가 먼저 상한에 닿아
BMS가 끊은 것**이다. 같은 불균형이 방전에서도 작동해 **약한 셀이 먼저 바닥을 치면
팩 전체가 차단**된다. "전압이 10.x V인데 왜 꺼지나"가 이것으로 설명됐다.

제품 스펙 자체도 물리적으로 모순이었다.

- 3S1P에서 3500mAh를 주장 → 셀 1개가 3500mAh여야 하는데 셀 단가만으로 판매가를 넘는다
- 팩 무게 135g 표기 → **정품 3500mAh 셀 3개만 해도 141g 이상**
- 3500mAh급의 연속 방전 한계는 8~10A인데 20A를 주장

치수(68×56×24mm)는 오히려 진짜 18650 3개임을 확인해줬다. 더 작은 셀로 속인 것이
아니라 **진짜 18650에 저급 내용물**이 들어간 것이고, 무게에서 역산하면 셀당 약 39g으로
정품 최하위급(44~45g)보다도 가볍다.

### 4.2 저장장치 정지 — USB 브릿지 문제

작업 중 파일시스템이 read-only로 전환되고 시스템이 응답하지 않는 사고가 반복됐다.
원인은 USB-SATA 브릿지(ASMedia)의 UAS 모드 문제로 좁혀졌다.

**해결**: microSD로 이전. 랜덤 IOPS가 79배 개선됐고 사고가 재발하지 않았다.

**부수적으로 배운 것**: systemd 하드웨어 워치독은 "디스크는 죽었는데 커널은 살아 있는"
고장을 못 잡는다 — PID 1이 계속 워치독을 갱신하기 때문이다. 이를 위해 별도 감시
프로세스를 만들었다(자식을 fork해 쓰기+동기화를 시키고 부모가 타임아웃을 재는 구조).

### 4.3 LiDAR 통신 불안정 — GPIO UART에서 USB로

LD06을 GPIO UART(`/dev/ttyAMA0`, 230400bps)에 직결했는데 커널 로그에 DMA 관련
버그와 input overrun이 반복됐다. USB 어댑터로 이전해 해결했다.

**이전 후 새로운 위험이 생겼다.** USB 직렬 장치가 2개(모터, LiDAR)가 되면서
`/dev/ttyUSB*` 번호가 **부팅 시 인식 순서로 정해지게** 됐다. 뒤바뀌면 주행 노드가
LiDAR 포트를 열어 **모터 명령을 LiDAR로 쏜다.** udev 규칙으로 VID:PID 기반 고정
심볼릭 링크(`/dev/lidar`, `/dev/motor`)를 만들어 차단했다.

### 4.4 라이다 자기 차폐 — 측정으로 배치를 결정

로봇 자신의 구조물이 LiDAR 시야를 가려 지도에 장애물로 박히는 문제가 있었다.

**자기 구조물을 환경과 구분하는 방법**: 로봇 구조물은 **로봇 좌표계에 고정**돼 있어
같은 각도에서 항상 같은 거리로 관측되고 분산이 매우 작다. 환경은 그렇지 않다.

| 조치 | 총 차폐 | 정면 ±30° 차폐 |
|---|---|---|
| 초기 (상판 거꾸로) | 91° | 31% |
| 하판 이전 | 41° | 5% |
| **전방 이동 (앞바퀴 축 선상)** | **34°** | **0%** |

⚠️ 정지 상태 측정만으로는 부족했다. 도크 충전 케이블과 소파를 자기 구조물로 오인한
적이 있다. **로봇을 손으로 한 바퀴 돌리면** 자기 구조물만 각도·거리가 고정되므로
확실히 갈린다. 같은 회전으로 지자기 하드아이언 보정도 동시에 수행했다.

### 4.5 직진 편차 — 원인이 세 개였다

로봇이 직진 명령에도 오른쪽으로 휘었다. 소프트웨어 보정값(`straight_trim`)을
**−0.4에서 +0.8까지 전 범위로 훑어도 이탈각이 4.5°밖에 안 변했고 부호조차 바뀌지
않았다.** 즉 그 방법으로는 손댈 수 없는 문제였다.

원인을 분리한 결과:

| 원인 | 성격 | 조치 | 결과 |
|---|---|---|---|
| 모터 1채널 구동 사망 | 커넥터 탈락 | 재체결 | 좌우 추력비 1.89 → 1.10 |
| 모터 1채널 기계적 드래그 | 일정 저항 토크 | PWM 오프셋 보정 | 좌우 불균형 8.1% → 1.4% |
| 바퀴 토(toe) 정렬 | 기구 | 나사 조정 | 이탈각 −5.7° → −2.2° |

**최종: −13° → −2.2° (83% 감소), 표준편차 0.9° → 0.2°**

정렬이 개선됐다는 **독립적인 증거**도 나왔다. 같은 명령·같은 시간인데 엔코더 카운트가
5122 → 5612(+9.6%)로 늘었다. **긁힘이 줄어 같은 PWM에 바퀴가 더 굴렀다는 뜻**이다.

토 정렬은 전진·후진 비대칭으로도 드러났다. 단순 좌우 불균형이면 두 방향의 크기가
같아야 하는데(부호만 반대), 전진 +3.5° / 후진 −9.7°로 **64% 차이**가 났다.
토는 **전진에서 자기정렬 방향으로 안정되고 후진에서 발산 방향으로 작용**하기 때문이다.

### 4.6 최적점 탐색 — cliff test

정렬 조정은 "좋아졌다"에서 멈추면 최적인지 알 수 없다. **부호가 뒤집힐 때까지
조정해서** 최적점을 사이에 가두는 방식(cliff test)을 썼다.

    조정 없음  −5.7°
    1차 조정   −2.2°   <- 최적점이 이 사이
    2차 조정   +3.5°   <- 부호 전환 = 지나침

같은 방법을 회전 데드존 탐색에도 적용했다. PWM을 임의 구간에서 끊었다가, **동작이
멈출 때까지 내려가서** 데드존이 230에서 49로 무너진 것을 발견했다. 임의로 자른 범위만
재면 그 밖을 모른 채 모델을 만들게 된다.

## 5. AI의 한계와 대응

이 절이 이 프로젝트에서 가장 실무적인 내용이다. **AI가 만든 오류를 걸러내는 것이
개발의 상당 부분을 차지했다.**

### 5.1 반복적으로 나타난 실패 유형

**(a) 지표는 정상인데 내용이 틀린 상태를 놓친다**

같은 유형의 문제가 4번 나왔다.

| 사례 | 겉보기 | 실제 |
|---|---|---|
| 지자기 센서 | 50Hz로 정상 발행 | 33초간 1654샘플이 **바이트 단위로 동일** = 센서 정지 |
| 스캔 필터 | `/scan` 10Hz 정상 | 파라미터 키 불일치로 **필터 체인이 빈 채 통과** |
| 맵 대시보드 | 토픽 정상 | 신선도 감시가 화면을 지움 |
| 배터리 충전기 | "완충" 녹색등 | 80%도 안 찬 상태에서 BMS가 차단 |

**교훈**: `ros2 topic hz`가 도는 것은 **센서가 살아있다는 증거가 아니다.**
값이 실제로 변하는지, 필터가 실제로 거르는지를 확인해야 한다.

**(b) 부품·환경 현황을 확인하지 않고 조언한다**

전압 센서 배선을 설명하면서 **이미 구매한 부품(INA219)이 아니라 계획 문서에 적힌
부품(ADS1115)** 기준으로 답했다. 이어서 데이지체인용 케이블이 있는데도 GPIO 직결을
제안했다. 부품 목록은 저장소에 있었지만 **읽지 않았다.**

**(c) 과거 상태를 현재 측정으로 단정한다**

모터 한 채널이 죽은 것을 오늘 발견하고 "이것이 어제 직진 편차의 원인"이라고 결론냈다.
그러나 사용자는 어제 시험 당시 4개가 모두 돌고 있었음을 **직접 관측**했다.
AI에게는 어제의 관측 기록이 없었다.

**(d) 자기 반론을 과신한다**

외부 기술 보고서를 검토하며 광학 플로우 센서 도입을 "보류"로 판단했다. 근거는
"광학 플로우는 병진만 측정하고 회전은 주지 않는다"였다. 기술적으로는 맞지만
**결론이 틀렸다** — 회전은 이미 자이로로 해결됐고, 미해결이던 병진을 정확히 그
센서가 채우기 때문이다. 외부 주장을 검증 없이 받지 않는 것과 **자기 반론을 검증 없이
확신하는 것**은 같은 오류다.

**(e) 도구 사용의 부작용을 예측하지 못한다**

- `pkill -f <패턴>`이 **그 명령을 실행하는 셸 자신도 매칭**해 작업 셸이 반복해서 죽었다
- DDS 공유메모리를 정리하며 `/proc/*/fd`만 확인하고 `/proc/*/maps`를 빠뜨려
  **살아있는 통신 상태를 삭제**했다(FastDDS는 mmap 후 fd를 닫는다)
- 측정 도구가 구독 연결을 기다리지 않아 초반 샘플이 누락됐고, 그 때문에
  **"첫 회차만 성적이 좋다"는 존재하지 않는 현상**을 쫓을 뻔했다

### 5.2 대응 방법

**(1) 실패를 사과가 아니라 도구로 막는다**

| 문제 | 만든 장치 |
|---|---|
| `pkill -f`가 자기 셸을 죽임 | `killproc.py` — 자기 자신과 조상 프로세스를 제외, 실행파일명 단위 매칭. `ros2` 같은 포괄적 이름은 거부 |
| 센서가 조용히 멈춤 | 원시값이 일정 시간 안 바뀌면 **발행을 중단**하고 재초기화. 죽은 값을 신선한 값으로 믿게 두지 않는다 |
| 측정 도구의 구독 누락 | 수신을 실제로 확인한 뒤 측정 시작 |
| 부품 현황 미확인 | 단일 기준 문서 + "하드웨어 조언 전 필독" 규칙 |

**(2) 결정을 이유와 함께 저장소에 남긴다**

AI는 세션이 바뀌면 대화를 기억하지 못한다. **대화에서 정한 것은 문서로 옮기지 않으면
사라진다.** 실제로 부품 선택 변경(ADS1115 → INA219)과 배선 방침(Qwiic 데이지체인)이
대화에만 있어서 다음 세션에서 통째로 유실됐다.

**(3) 검증 수단을 실물에서 분리한다**

알고리즘 검증을 실물 로봇으로 하다가 벽에 밀어넣었다. 이후 역할을 나눴다.

| 검증 대상 | 수단 |
|---|---|
| 로직 (목표 선정, 비용함수, 필터 기하) | rosbag 재생, 2D 시뮬레이터 |
| 물리 (미끄러짐, 자기 차폐, 스캔 왜곡, 전력) | **실물만** |

⚠️ 다만 "시뮬에서 되니까 된다"는 위험하다. Nav2의 MPPI 컨트롤러가 시뮬에서는
완벽한데 실물 디프드라이브에서 흔들린다는 보고가 실제로 있다.

**(4) 측정 조건을 함께 기록한다**

초기 회전 측정에 배터리 전압을 안 남겨서, 나중에 "개선폭이 13.6%인가 300%인가"를
엄밀히 검증할 수 없게 됐다. 모터 회전수는 인가 전압에 거의 비례하므로 **전압 없는
측정값은 다음 측정과 비교가 불가능하다.**

**(5) 외부 산출물을 현재 상태와 대조한다**

외부 AI가 작성한 기술 보고서 7편을 검토했는데, 그중 한 편은 **7개 제안 중 3개가 이미
적용된 항목**이었고 진단에 사실관계 오류가 2건 있었다. 예를 들어 "실내 지자기 교란으로
자이로 적분 오차가 누적된다"는 서술은 틀렸다 — 자력계와 자이로는 별개 센서이고 해당
시스템의 EKF는 자력계를 입력으로 쓰지 않는다. 실제로 자기 편향이 지구 자기장의 3배까지
올라간 상태에서도 자이로 추종 오차는 7.1%로 정상이었다.

또 한 항목은 **이 시스템에서는 반대로 작용**했다. 루프 클로저 임계값을 높여 유령 벽을
막자는 제안이었는데, 임계값을 올리면 루프 클로저가 줄어든다. 그런데 측정해보니 이
시스템의 문제는 **루프 클로저가 부족한 것**이었다(포즈 그래프 노드 40개에 추가 제약
11개, 특정 방의 벽 정렬도 58.2% vs 나머지 79.6%).

## 7. 얻은 경험

### 7.1 학교에서 배운 것의 실무 적용

| 학습 내용 | 적용 |
|---|---|
| 마찰과 모멘트 | 스키드 스티어 스크럽 토크 `M = μmgL/2`로 축간거리 단축을 설계 |
| 모터 특성 곡선 | 스톨 근처 동작점에서 부하 감소가 속도에 비선형으로 작용하는 것을 해석 |
| 제어 이론 (루프 이득) | 플랜트 이득 1.76배 변화에 맞춰 게인을 1/1.76로 조정, 실측 최적점과 일치 |
| 차량 동역학 (토 정렬) | 전진·후진 비대칭으로 토 오차를 식별 |
| 계측 설계 | 세 가설이 전류에 따라 다른 흔적을 남긴다는 점을 이용해 원인 분리 |
| 오차 해석 | 측정 조건 통제, 반복 측정과 표준편차로 유의성 판단 |

### 7.2 AI 협업에서 얻은 판단 기준

1. **AI는 계산과 구현을 가속하지만 물리적 사실을 대신 확인해주지 않는다.**
   부품이 무엇인지, 커넥터가 빠졌는지, 바퀴가 뻑뻑한지는 사람이 봐야 한다.

2. **AI가 만든 결론에는 반드시 "무엇으로 확인할 수 있는가"를 붙여야 한다.**
   실측으로 갈릴 수 있는 항목은 "채택/보류"가 아니라 **어떤 측정으로 결론 낼지**를
   정하는 것이 낫다.

3. **같은 실수가 두 번 나오면 도구나 규칙으로 막는다.** 사과나 주의로는 반복된다.

4. **기록되지 않은 결정은 존재하지 않는 것과 같다.** AI 협업에서는 특히 그렇다.

5. **정상 신호와 정상 동작은 다르다.** 이 프로젝트에서 가장 값비쌌던 버그들은
   모두 "지표는 정상인데 내용이 틀린" 유형이었다.

### 7.3 전공자로서의 관점

이 프로젝트에서 소프트웨어로 해결한 것과 기구로 해결한 것을 비교하면:

| 개선 | 수단 | 효과 |
|---|---|---|
| 축간거리 125 → 108mm | **기구** | 회전 각속도 +143~309% |
| LiDAR 전방 이동 | **기구** | 정면 차폐 5% → 0% |
| 바퀴 토 정렬 | **기구** | 직진 이탈 −5.7° → −2.2° |
| 피드포워드 모델 + 게인 재튜닝 | 소프트웨어 | 추종 오차 25.6% → 7.1% |
| 채널별 PWM 오프셋 | 소프트웨어 | 좌우 불균형 8.1% → 1.4% |

**가장 큰 개선은 기구에서 나왔다.** 소프트웨어 보정은 기구가 만든 오차를 완전히
지우지 못한다 — 실제로 직진 보정값을 전 범위로 훑어도 부호조차 바뀌지 않은 구간이
있었고, 정지 시 감속은 마찰이 지배하므로 개입할 수단 자체가 없다.

**휘어 있는 기구에 센서를 추가해 보정하는 것은 증상을 덮는 것이다.** 순서는
기구를 먼저 맞추고, 남은 오차를 소프트웨어로 잡는 것이다.
