## 2. 남은 문제 — 우선순위별

### 2.1 [최우선] 휠 오도메트리 동결 — 물리적 조치 + 검증 완료 (2026-08-29)

실물 매핑 시험 2회(거실→A방→복귀) 모두에서 같은 패턴 관측: **`/odom`의 요각이
수십 초간 완전히 고정**되는 동안 **EKF는 계속 갱신됨**.

- 1차 시험: 후반 ~35초간 `/odom` 요각이 +136.8°로 고정. 실제 순변위는 0(사용자가
  "비슷한 곳"에 도착, 완전 복귀는 아님)인데 시스템은 4m 어긋난 걸로 인식.
- 2차 시험(motor_dashboard 끄고 "깨끗한" 조건으로 재현 시도): 처음엔 motor_dashboard가
  원인이라 의심했으나 **오판이었음** — `motor_dashboard.py`는 이미 예전에
  `/cmd_vel` 발행 방식으로 바뀌어서(`340fdc5`) 시리얼 포트를 직접 안 건드림.
  motor_dashboard를 끈 채로도, 다시 켠 채로도 **동일한 "동결" 패턴이 재현**됨
  (후반 ~13초간 `/odom` 요각 +32.4°로 고정). 즉 **motor_dashboard와 무관**함이
  확인됨.
- `ekf.yaml`의 `odom0_config`가 `x,y,vx`는 True, `yaw,vyaw`는 False로 설계돼있어서
  ("전진거리=휠, 회전각=자이로" 원칙) — 휠 오도메트리가 동결되면 **EKF의 x,y
  위치 추정도 그 구간만큼 실제 이동을 놓친다.** 이게 실제 정답과 크게 어긋난
  최종 위치의 가장 유력한 메커니즘.

**아직 못 잡은 것**: 정확한 실패 지점(시리얼 read 실패? 진짜 물리적 바퀴 걸림?
`_read_encoder()`의 `$upload:` 프로토콜 상태 꼬임?). `_on_odom_timer`에 정지
경고는 추가해뒀는데(`diff_drive_node.py`, 2026-08-24) 2차 시험에서 **이 경고가
안 찍혔다** — 즉 "새 시리얼 응답은 오는데 카운트값이 우연히 같다"거나 "코드
경로가 다르다"일 수 있어 재진단이 더 필요함. 원시 엔코더 카운트(`/encoder_counts`
토픽)를 이번엔 안 로깅해서 확증은 못 함 — **다음 시험엔 이것도 같이 기록할 것.**

#### 배제 시험 (2026-08-24 밤, Phase A/B) — 원인 후보를 크게 좁힘

원인불명 상태를 좁히려고 단계적 배제 시험을 설계·실행함. 각 단계는 "이 변수가
없어도 재현되나"를 확인하는 방식.

- **CPU 부하설 반증**: `power_trace.csv`(상시 1초 간격 CPU% 기록)로 두 동결
  구간을 직접 대조 — 두 구간 모두 CPU 46~48%로 완전히 평평, 스파이크 없음.
  SLAM/Ceres 솔버로 인한 CPU 경합은 원인이 아님.
- **Phase A(정지, 조종·SLAM 없음, 10분)**: `_read_encoder()`에 실패 진단 로깅
  추가(실패 시작/heartbeat/복구 시 원시 바이트 기록, `diff_drive_node.py`) 후
  10분 순수 대기 — **재현 안 됨.** 순수 시간경과/정지 상태 배경 노이즈만으로는
  안 나옴.
- **Phase B(도크 위 무부하 모터 구동, 5분)**: 바퀴 뜬 상태로 전진(0.3m/s)/
  후진/제자리회전(0.6rad/s) 37사이클 반복 — **재현 안 됨.** 모터 전류/PWM
  스위칭 자체(바닥 부하 없이)도 원인이 아님.
- **결론**: 정지 상태(A)도, 모터 전류 단독(B)도 아니고 **오늘 재현된 두 번 다
  "실제 바닥 하중이 걸린 주행" 중에만 발생**했다. 남은 핵심 변수는 **바닥
  접지 하중/진동**뿐 — USB 케이블·커넥터의 기계적 접촉불량이 유력 후보로
  좁혀짐(모터 드라이버 보드 자체의 전압 처짐 가능성도 배제 안 됨, 둘 다
  "실제 하중 걸릴 때만" 나온다는 점과 부합).

#### Phase E 실행 결과 — 접촉불량 재현 + 긴급정지 실전 (2026-08-29)

당초 계획한 E-1~E-4 순서 그대로는 아니고, 재현 시도를 반복하며 실제로는 이렇게
진행했다:

1. **도크 위 일반 케이블 스트레스 + 랜덤 구동 동시 진행** — 이때 나온 로그를
   분석한 게 `docs/calibration/phaseE2_20260829_1141.csv`. 이 시점엔 원시
   채널 로깅이 없어 **어느 케이블/채널이 원인인지는 특정 못 한 채로** 동결
   66건(최장 172.6초)만 확인함.
2. **사용자 가설 기반 재시험**: "M1이 연결 안 된 상태에서 문제가 없었다면 M1이
   범인일 가능성이 높다" — M1만 연결 해제한 대조군에서 문제 없음을 먼저 확인한
   뒤, M1을 재연결하고 **M1 케이블만 흔들어 접촉이 되었다 안 되었다를 반복**하며
   재현 시도(이전 일반 스트레스 시험과 달리 M1 하나로 자극을 좁힌 시험).
3. **⚠️ 시험 중 실제 통신 두절 재현 + 긴급 정지 오작동**: "M1이 또 연결이
   안되었어. 멈추고 체크해보자"라는 요청에 `killproc.py`로 정지를 시도했으나
   프로세스 이름 매칭 실패로 실제로는 안 멈췄었고(heredoc으로 띄운 노드라
   `ps`에 안 잡힘), 수 분 뒤 엔코더 데이터를 다시 볼 때에야 여전히 구동 중임을
   발견해 PID를 직접 확인 후 `kill -TERM`으로 정지함(정지 후 엔코더 4채널
   rate=0 확인). **교훈: 안전 관련 정지 명령은 반드시 실행 직후 결과를
   재확인할 것 — "멈출게"라고 말하고 확인 없이 넘어가면 안 됨.**
4. **원시 4채널 로깅 추가 후 M1 시험 재실행** (`loop_gyro_diag.py`에
   `/wheel_encoders` 구독 추가, `enc_m1~m4` 컬럼) — 결과는 아래 "원인 규명" 참고.

#### 원인 규명 — 4채널 동기화 정지, "M1만 고착"이 아니었다 (2026-08-29)

`docs/calibration/phaseE3_20260829_1213_rawenc.csv`(M1 케이블만 흔든 5분 시험,
`enc_m1~m4` 원시값 포함)를 분석해서 2026-08-24에 못 잡았던 지점("이 경고가 안
찍혔다 — 재진단 필요")을 확정했다.

- **동결 4건 재현**(1.4~2.0초). 매번 **4채널 값이 정확히 같은 샘플에서 동시에
  멈췄다가 동시에 풀렸다**(`enc_m1~m4` 전부 같은 인덱스에서 변화). 즉 당초
  가정("M1 채널 하나만 값이 고착돼서 `d_left`/`d_right` 계산이 틀어진다")은
  틀렸다 — 실제로는 **M1을 건드리면 4채널 응답 전체가 마치 하나의 스냅샷을
  반복하듯 동시에 멎는다.**
- **`/wheel_encoders`(원시값)도 `/odom`과 완전히 같은 구간에서 얼어붙는다** —
  odom 계산/발행(`_on_odom_timer`)의 문제가 아니라 그보다 상류인
  `_read_encoder()` 시리얼 왕복이 새 값을 못 받아오는 것.
- **그런데도 "엔코더 응답 파싱 실패" 경고는 이 4건 전부 단 한 번도 안 찍혔다**
  (journalctl로 4개 구간 전부 직접 대조). `_read_encoder()`가 매번 파싱 가능한
  `$MAll:` 라인을 리턴했다는 뜻 — **응답이 없는 게 아니라, 갱신 안 된 스냅샷을
  유효한 응답인 것처럼 반복해서 돌려받는다.** 기존 경고 두 개(파싱 실패,
  `_on_odom_timer`의 정체 경고) 모두 "응답이 아예 없다"만 감지하지 "응답은
  오는데 값이 안 바뀐다"는 못 잡는 구조라 이번까지 조용히 넘어갔던 것.
- **M1 하나만 자극해도 재현된다** — 이전 `phaseE2`(일반 스트레스, 66건·최장
  172.6초)는 어느 케이블이 원인인지 특정 못 했지만, 이번 `phaseE3`는 M1만
  건드려서 4건이 나왔으므로 **M1 단독으로 충분한 방아쇠임이 처음으로 확정**됐다.
  지속시간이 이번엔 훨씬 짧았는데(2초 이내 vs 최장 172.6초), 두 시험이 스트레스
  강도·방식이 달라 엄밀한 비교는 아니지만 접촉 불량 정도에 비례해 짧게도
  길게도 나타나는 것으로 보인다.
- **남은 질문(미확정)**: 이 "멎은 스냅샷"이 드라이버 보드 쪽에서 만들어지는지
  (보드 MCU의 공유 인터럽트/메인루프가 M1 신호 이상으로 잠깐 멎으면서 4채널
  전부 갱신을 못 하는 것) 아니면 Pi 쪽 시리얼 버퍼링 문제인지(`reset_input_buffer()`가
  USB-시리얼 칩 내부 큐까지 완전히 못 비워서 오래된 프레임을 다시 읽는 것)는
  이번 데이터로는 구분 안 된다 — `_read_encoder()`의 `raw` 원시 바이트를
  타임스탬프와 함께 남기면 구분 가능하나, 어느 쪽이든 **M1이 방아쇠라는
  상관관계는 이미 확정**이라 물리적 조치의 우선순위엔 영향 없음.

**다음 단계**: M1 커넥터/배선의 물리적 접촉 불량 자체를 고치는 것(재체결, 압착
재작업, 케이블 교체 등)이 다음 행동 — 위 "남은 질문"과 무관하게 진행 가능하다.
원시 바이트 로깅으로 정확한 정지 위치(보드 vs Pi)를 더 파는 것은 선택사항이며,
물리적 조치 후에도 재현되면 그때 우선순위를 올릴 것.

#### 물리적 조치 + 검증 — 재현 없음 확인 (2026-08-29)

사용자가 M1 커넥터/배선을 재체결. 곧바로 도크(무부하) → 바닥(실하중) 순으로
`loop_gyro_diag.py`(원시 4채널 + odom + 배터리 로깅) 켠 채 검증 시험을 진행했다.

- **도크 시험** (5분, 랜덤 전진/후진/회전): odom_yaw 동결 **0건**(0.3초 기준으로도
  0건). M1 원시값이 개별적으로 잠깐(0.3~0.86초) 안 바뀐 구간이 12건 있었지만,
  전부 시험 시작 14초 안에만 몰려 있고 그때마다 M2/M3/M4는 수백~1700카운트씩
  정상적으로 움직이고 있었다 — 4채널 동기화 정지 신호는 아니고 정상적인 저속
  구간 노이즈. 배터리 11.98~12.12V.
- **바닥 시험** (90초, 저속 랜덤): odom_yaw 동결 0.3초 기준 14건 있었으나
  **전부 그 순간에도 4채널 원시값이 정상적으로 움직이고 있었음을 확인**
  (동기화 정지 0건). ekf_yaw가 -179.9~179.7도 전 범위를 실제로 스윕해
  로봇이 진짜로 움직였음도 함께 확인. 배터리 11.66~11.96V.
- 로그: `docs/calibration/postfix_20260829_1410.csv`(도크),
  `docs/calibration/floor_20260829_1418.csv`(바닥) — git엔 미포함(용량, 로컬 보관).

**결론**: 무부하·실하중 두 조건 모두에서 "4채널 동기화 정지" 패턴이 완전히
사라졌다. M1 접촉불량이 원인이었다는 게 물리적 조치로 재현·검증까지 끝났다.
재발 시엔 이 항목을 다시 열 것 — 특히 케이블에 스트레스가 반복되는 실사용
환경(도어 문턱, 카펫 경계 등)에서 장기 재현 여부는 아직 못 봤다.

**왜 최우선이었나**: 이건 "몇 % 부정확하다"가 아니라 **몇 초에서 몇십 초씩
데이터가 통째로 사라지는 현상**이었다. rf2o든 광류든 어떤 보조 센서를 얹어도,
메인 파이프라인이 이렇게 조용히 멈추면 그 센서 데이터도 같이 무의미해진다.
원인 규명 + 물리적 조치 + 검증까지 끝났으므로 이 항목은 종료.

### 2.2 회전 폐루프 잔여 불안정성 (~18%, 우선순위 중)
오늘 고친 뒤에도 방향반전 재현시험에서 데드존 경고가 3/23 남음. 크기는 작아졌지만
0은 아님 — 위 2.1이 해결된 뒤에 남는 노이즈인지 별개 문제인지 재확인 필요.

### 2.3 거리 스케일 오차 가설 (~2%, 우선순위 낮음)
`wheel_radius` 보정 후보(67→~68.5mm). 실측 반복(n≥5) 후 결정. 위 2.1보다 영향이
훨씬 작음 — 급하지 않음.

## 3. Davi 제안 재검토 (2026-08-17 보고서 2건 기준)

## 4. 외부 리서치 — 남들은 어떻게 푸는가

**`rf2o_laser_odometry`** (MAPIR Lab, ICRA 2016 논문 기반, [GitHub](https://github.com/MAPIRlab/rf2o_laser_odometry)):
- 라이다 스캔만으로 평면 오도메트리 추정, **휠 슬립과 완전 무관**(바퀴가 헛돌아도
  주변 벽면 형상 변화로 실제 변위 계산).
- 단일 코어 **0.9ms**, 새 하드웨어 0원 — 이미 있는 LD06을 그대로 씀.
- ROS2(jazzy) 포크 존재 확인([linuxsen/rf2o_laser_odometry_ros2](https://github.com/linuxsen/rf2o_laser_odometry_ros2)).
- **가장 비용 대비 가치가 높은 후보** — Davi가 이미 1순위로 추천했었는데
  한 번도 시도 안 됨.

**광학 플로우 센서(PMW3901)**: 실사용기 조사 결과([Pimoroni 포럼](https://forums.pimoroni.com/t/pmw3901-optical-flow-for-ground-based-robot/13600)) —
- 지면 로봇에 쓸 수는 있지만 **오차 약 10%, 표면(러그/나무 등)에 따라 편차**,
  가끔 값이 튀는 현상 보고됨. 최소 장착 높이 88mm에선 정확도가 별로 안 좋고,
  35mm처럼 훨씬 가까이 달아야 나음 — **PMW3901보다 근접용 파생품 PAA5100JE
  (15~35mm 사거리)가 지면 로봇엔 더 적합**해 보임(PMW3901은 원래 드론용).
- **결론**: "휠 슬립 원천 종결"이라는 Davi의 표현은 과장 — 실제로는 자체 오차와
  필터링이 필요한 또 하나의 불완전한 센서다. rf2o가 **비용 0원에 이미 검증된
  알고리즘**이라 먼저 시도할 이유가 명확함. 광학플로우는 rf2o로도 부족할 때
  재검토.

**EKF 슬립 공분산 튜닝** (학계 문헌 조사): 고정 시간창(우리가 오늘 쓴 150ms류)보다
**Mahalanobis 거리 기반 동적 공분산**(측정값이 현재 상태추정과 얼마나 어긋나는지
실시간으로 재서 그 정도에 비례해 공분산을 올리는 방식)이 더 원칙적인 표준
기법으로 확인됨. 오늘 쓴 고정창 방식은 실용적 근사치이지 정석은 아님 — 나중에
더 다듬을 여지 있음.

## 5. 권고 순서

> ⚠️ **2026-08-29 갱신**: 아래 1번(동결)이 해결·검증 완료되면서 병목이
> "장주기 요 드리프트 + 루프클로저 부재"로 이동함. 최신 평가와 계획은
> **`docs/midterm_review_20260829.md`**가 기준이다 — 아래는 이력으로만 보존.

1. **[최우선] 휠 오도메트리 동결 원인 확정** — 원시 엔코더 카운트까지 같이
   로깅하며 재현. 시리얼 read 실패인지, 물리적 걸림인지, 프로토콜 상태 꼬임인지
   구분할 것. **이게 안 잡히면 다른 어떤 개선도 신뢰 못 함.**
2. **`rf2o_laser_odometry` 도입 시도** — 비용 0원, 검증된 알고리즘, 이미
   Davi/Remi 둘 다 동의했던 항목인데 안 해봄. 2.1이 해결되면 바로 다음 순서.
3. 회전 폐루프 잔여 불안정성(2.2) — 2.1 해결 후 재측정, 필요시 슬립 감지
   공분산(Davi 제안) 적용 검토.
4. 거리 스케일 가설(2.3) — 급하지 않음, 시간 날 때 반복측정.
5. **ZUPT 지자기 헤딩 리셋** — 이제 방위 부호가 맞으니 재검토 가치 있음.
   다만 위 1~3보다 급하지 않음(도크 한정 스코프로 리스크는 낮았던 제안).
6. **광학플로우/ToF 하드웨어**: 1호기엔 보류. rf2o 시도 후 그래도 부족하면
   그때 2호기 설계에 반영 검토(비용도 저렴하니 아예 배제할 필요는 없음).
