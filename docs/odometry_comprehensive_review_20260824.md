## 2. 남은 문제 — 우선순위별

### 2.1 [최우선] 휠 오도메트리 동결 — 원인 미확정, 두 번 재현됨

실물 매핑 시험 2회(거실→A방→복귀) 모두에서 같은 패턴 관측: **`/odom`의 요각이
수십 초간 완전히 고정**되는 동안 **EKF는 계속 갱신됨**.

- 1차 시험: 후반 ~35초간 `/odom` 요각이 +136.8°로 고정. 실제 순변위는 0(사용자가
  "비슷한 곳"에 도착, 완전 복귀는 아님)인데 시스템은 4m 어긋난 걸로 인식.
- 2차 시험(motor_dashboard 끄고 "깨끗한" 조건으로 재현 시도): 처음엔 motor_dashboard가
  원인이라 의심했으나 **오판이었음** — `motor_dashboard.py`는 이미 예전에
  `/cmd_vel` 발행 방식으로 바뀌어서(`340fdc5`) 시리얼 포트를 직접 안 건드림.
  motor_dashboard를 끈 채로도, 다시 켠 채로도 **동일한 "동결" 패턴이 재현**됨
  (후반 ~13초간 `/odom` 요각 +32.4°로 고정). 즉 **motor_dashboard와 무관**함이
  확인됨.
- `ekf.yaml`의 `odom0_config`가 `x,y,vx`는 True, `yaw,vyaw`는 False로 설계돼있어서
  ("전진거리=휠, 회전각=자이로" 원칙) — 휠 오도메트리가 동결되면 **EKF의 x,y
  위치 추정도 그 구간만큼 실제 이동을 놓친다.** 이게 실제 정답과 크게 어긋난
  최종 위치의 가장 유력한 메커니즘.

**아직 못 잡은 것**: 정확한 실패 지점(시리얼 read 실패? 진짜 물리적 바퀴 걸림?
`_read_encoder()`의 `$upload:` 프로토콜 상태 꼬임?). `_on_odom_timer`에 정지
경고는 추가해뒀는데(`diff_drive_node.py`, 2026-08-24) 2차 시험에서 **이 경고가
안 찍혔다** — 즉 "새 시리얼 응답은 오는데 카운트값이 우연히 같다"거나 "코드
경로가 다르다"일 수 있어 재진단이 더 필요함. 원시 엔코더 카운트(`/encoder_counts`
토픽)를 이번엔 안 로깅해서 확증은 못 함 — **다음 시험엔 이것도 같이 기록할 것.**

#### 배제 시험 (2026-08-24 밤, Phase A/B) — 원인 후보를 크게 좁힘

원인불명 상태를 좁히려고 단계적 배제 시험을 설계·실행함. 각 단계는 "이 변수가
없어도 재현되나"를 확인하는 방식.

- **CPU 부하설 반증**: `power_trace.csv`(상시 1초 간격 CPU% 기록)로 두 동결
  구간을 직접 대조 — 두 구간 모두 CPU 46~48%로 완전히 평평, 스파이크 없음.
  SLAM/Ceres 솔버로 인한 CPU 경합은 원인이 아님.
- **Phase A(정지, 조종·SLAM 없음, 10분)**: `_read_encoder()`에 실패 진단 로깅
  추가(실패 시작/heartbeat/복구 시 원시 바이트 기록, `diff_drive_node.py`) 후
  10분 순수 대기 — **재현 안 됨.** 순수 시간경과/정지 상태 배경 노이즈만으로는
  안 나옴.
- **Phase B(도크 위 무부하 모터 구동, 5분)**: 바퀴 뜬 상태로 전진(0.3m/s)/
  후진/제자리회전(0.6rad/s) 37사이클 반복 — **재현 안 됨.** 모터 전류/PWM
  스위칭 자체(바닥 부하 없이)도 원인이 아님.
- **결론**: 정지 상태(A)도, 모터 전류 단독(B)도 아니고 **오늘 재현된 두 번 다
  "실제 바닥 하중이 걸린 주행" 중에만 발생**했다. 남은 핵심 변수는 **바닥
  접지 하중/진동**뿐 — USB 케이블·커넥터의 기계적 접촉불량이 유력 후보로
  좁혀짐(모터 드라이버 보드 자체의 전압 처짐 가능성도 배제 안 됨, 둘 다
  "실제 하중 걸릴 때만" 나온다는 점과 부합).

#### 다음 세션 — Phase E: 접촉불량 여부 확인 (착수 지점)

목표: USB 케이블/커넥터의 기계적 접촉 문제인지, 모터 드라이버 보드 자체
(전압 처짐 등) 문제인지 구분.

1. **E-1 (무부하, 손으로 케이블 스트레스)**: 도크 위, 모터 정지 상태(진단
   로깅 켠 채)에서 Pi↔모터 드라이버 USB 케이블/커넥터를 손으로 여러 방향
   당기고 흔들며 5분 관찰. **여기서 실패가 뜨면 → 순수 기계적 접촉 문제
   확정**(전기적 부하와 무관하다는 뜻이므로 Phase B 결과와도 모순 없음 —
   B는 케이블을 안 건드렸으니까).
2. **E-2 (dmesg 동시 캡처)**: Phase C/D(실주행) 재실행 시 `dmesg -w`를 같이
   띄워서, 동결 시각에 USB 재열거/디스커넥트 커널 로그(`device descriptor
   read/64, error -71` 류)가 겹치는지 확인 — 겹치면 하드웨어 링크 단절 확정.
3. **E-3 (케이블 고정 A/B)**: USB 커넥터를 케이블타이/테이프로 물리적으로
   고정한 뒤 Phase D(오늘과 동일 조건: 실주행+SLAM)를 재실행, 고정 전후
   발생 빈도 비교.
4. **E-4 (재체결)**: 케이블을 뽑았다 다시 꽂고(접촉면 리셋) Phase D 재실행 —
   산화/먼지에 의한 접촉 저하였다면 이걸로 개선될 것.

E-1이 가장 저비용·저위험이라 다음 세션 시작점으로 적합. 재현되면 바로
원인 확정, 안 되면 Phase C/D(실주행)로 넘어가 E-2~E-4 순서로 진행.

**왜 최우선인가**: 이건 "몇 % 부정확하다"가 아니라 **몇십 초씩 데이터가 통째로
사라지는 현상**이다. rf2o든 광류든 어떤 보조 센서를 얹어도, 메인 파이프라인이
이렇게 조용히 멈추면 그 센서 데이터도 같이 무의미해진다. 원인을 모른 채로
넘어가면 안 됨.

### 2.2 회전 폐루프 잔여 불안정성 (~18%, 우선순위 중)
오늘 고친 뒤에도 방향반전 재현시험에서 데드존 경고가 3/23 남음. 크기는 작아졌지만
0은 아님 — 위 2.1이 해결된 뒤에 남는 노이즈인지 별개 문제인지 재확인 필요.

### 2.3 거리 스케일 오차 가설 (~2%, 우선순위 낮음)
`wheel_radius` 보정 후보(67→~68.5mm). 실측 반복(n≥5) 후 결정. 위 2.1보다 영향이
훨씬 작음 — 급하지 않음.

## 4. 외부 리서치 — 남들은 어떻게 푸는가

**`rf2o_laser_odometry`** (MAPIR Lab, ICRA 2016 논문 기반, [GitHub](https://github.com/MAPIRlab/rf2o_laser_odometry)):
- 라이다 스캔만으로 평면 오도메트리 추정, **휠 슬립과 완전 무관**(바퀴가 헛돌아도
  주변 벽면 형상 변화로 실제 변위 계산).
- 단일 코어 **0.9ms**, 새 하드웨어 0원 — 이미 있는 LD06을 그대로 씀.
- ROS2(jazzy) 포크 존재 확인([linuxsen/rf2o_laser_odometry_ros2](https://github.com/linuxsen/rf2o_laser_odometry_ros2)).
- **가장 비용 대비 가치가 높은 후보** — Davi가 이미 1순위로 추천했었는데
  한 번도 시도 안 됨.

**광학 플로우 센서(PMW3901)**: 실사용기 조사 결과([Pimoroni 포럼](https://forums.pimoroni.com/t/pmw3901-optical-flow-for-ground-based-robot/13600)) —
- 지면 로봇에 쓸 수는 있지만 **오차 약 10%, 표면(러그/나무 등)에 따라 편차**,
  가끔 값이 튀는 현상 보고됨. 최소 장착 높이 88mm에선 정확도가 별로 안 좋고,
  35mm처럼 훨씬 가까이 달아야 나음 — **PMW3901보다 근접용 파생품 PAA5100JE
  (15~35mm 사거리)가 지면 로봇엔 더 적합**해 보임(PMW3901은 원래 드론용).
- **결론**: "휠 슬립 원천 종결"이라는 Davi의 표현은 과장 — 실제로는 자체 오차와
  필터링이 필요한 또 하나의 불완전한 센서다. rf2o가 **비용 0원에 이미 검증된
  알고리즘**이라 먼저 시도할 이유가 명확함. 광학플로우는 rf2o로도 부족할 때
  재검토.

**EKF 슬립 공분산 튜닝** (학계 문헌 조사): 고정 시간창(우리가 오늘 쓴 150ms류)보다
**Mahalanobis 거리 기반 동적 공분산**(측정값이 현재 상태추정과 얼마나 어긋나는지
실시간으로 재서 그 정도에 비례해 공분산을 올리는 방식)이 더 원칙적인 표준
기법으로 확인됨. 오늘 쓴 고정창 방식은 실용적 근사치이지 정석은 아님 — 나중에
더 다듬을 여지 있음.

## 5. 권고 순서

1. **[최우선] 휠 오도메트리 동결 원인 확정** — 원시 엔코더 카운트까지 같이
   로깅하며 재현. 시리얼 read 실패인지, 물리적 걸림인지, 프로토콜 상태 꼬임인지
   구분할 것. **이게 안 잡히면 다른 어떤 개선도 신뢰 못 함.**
2. **`rf2o_laser_odometry` 도입 시도** — 비용 0원, 검증된 알고리즘, 이미
   Davi/Remi 둘 다 동의했던 항목인데 안 해봄. 2.1이 해결되면 바로 다음 순서.
3. 회전 폐루프 잔여 불안정성(2.2) — 2.1 해결 후 재측정, 필요시 슬립 감지
   공분산(Davi 제안) 적용 검토.
4. 거리 스케일 가설(2.3) — 급하지 않음, 시간 날 때 반복측정.
5. **ZUPT 지자기 헤딩 리셋** — 이제 방위 부호가 맞으니 재검토 가치 있음.
   다만 위 1~3보다 급하지 않음(도크 한정 스코프로 리스크는 낮았던 제안).
6. **광학플로우/ToF 하드웨어**: 1호기엔 보류. rf2o 시도 후 그래도 부족하면
   그때 2호기 설계에 반영 검토(비용도 저렴하니 아예 배제할 필요는 없음).
