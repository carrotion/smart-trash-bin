# 펌웨어·플릿·수명 관리 체계

작성 2026-08-17. 배경: 부팅 디스크를 microSD로 이관하면서 "SD는 소모품"이라는
전제가 생겼고, 2호기·3호기 제작을 앞두고 **소프트웨어를 어떻게 입힐 것인가**를
정해둘 필요가 생김.

이 문서는 가전제품의 펌웨어 모델(공장 이미지 → OTA 업데이트 → 고장 시 부품 교체)을
이 프로젝트에 맞게 옮긴 설계다.

---

## 0. 먼저 측정한 것 (2026-08-17 실측)

설계 전에 "우리가 카드에 얼마나 쓰고 있는가"를 쟀다. 추측으로 시작하면 엉뚱한 걸
최적화하게 된다.

**유휴 상태 쓰기량**: 3.05 GB/day = **연 1.0 TB**

**쓰기 주체 상위** (60초 측정, 실제 디스크 쓰기 기준):

| 프로세스 | 쓰기량 | 성격 |
|---|---|---|
| antigravity IDE 서버 | **204 MB/h** (4.9 GB/day) | 개발 전용 |
| VS Code 서버 | 3.5 MB/h | 개발 전용 |
| `power_monitor.py` | 3.5 MB/h | 로봇 상시 |

**핵심 발견: 카드 수명을 갉아먹는 주범은 로봇 소프트웨어가 아니라 개발 도구다.**
IDE 원격 서버 하나가 로봇 전체 스택보다 50배 넘게 쓴다.

→ **개발 유닛과 배포 유닛은 수명 프로파일이 근본적으로 다르다.** 이걸 하나의
   기준으로 관리하면 안 된다. 배포 유닛의 예상 수명을 개발 유닛 데이터로 추정하면
   심하게 과소평가하게 된다.

## 1. 3계층 모델

변경 주기가 다른 것을 같은 방식으로 배포하면 안 된다. 세 층으로 나눈다.

| 계층 | 내용 | 변경 주기 | 배포 방식 | 롤백 |
|---|---|---|---|---|
| **베이스 이미지** | OS, ROS2 Jazzy, 의존성, 서비스 유닛 | 수주~수개월 | 카드 이미지 굽기 | 이전 이미지로 재굽기 / 카드 교체 |
| **애플리케이션** | `smart-trash-bin` 저장소 + 빌드 산출물 | 매일 | `git fetch` + `colcon build` + 서비스 재시작 | 이전 태그로 checkout |
| **유닛 설정** | 이 로봇 고유의 식별자·보정값·자격증명 | 유닛마다 1회 + 재보정 시 | 첫 부팅 프로비저닝 | 백업본 복원 |

애플리케이션 업데이트가 절대 다수를 차지한다. 그건 이미 git이라 사실상 OTA가
갖춰져 있다 — 정식화만 하면 된다.

## 2. ⚠️ 가장 중요한 것: 유닛 고유값을 코드에서 분리하라

**이 프로젝트에서 가장 놓치기 쉬운 지점이다.** 지금 저장소에는 *1호기에서 실측한
상수*가 코드와 설정 파일에 그대로 박혀 있다:

| 값 | 현재 위치 | 왜 유닛마다 다른가 |
|---|---|---|
| `straight_trim: 0.6` | `diff_drive_node.py` | 모터 개체차·기계 얼라인먼트. 1호기에서 cliff test로 측정한 값 |
| `turn_boost: 1.4` | `diff_drive_node.py` | 바퀴 마찰·무게중심 |
| 라이다 차폐 구간(9개) | 배선·구조물 배치 | 조립할 때마다 달라짐 |
| `polygon: ±0.105` | `scan_self_filter` (laser_filters) | 차체 반폭 0.11m에서 5mm 안쪽. 기체 크기가 다르면 바뀐다 |
| 자이로 바이어스 | 시작 시 자동 측정 | 이미 분리돼 있음 ✓ |
| `robot_radius: 0.15` | `nav2_params.yaml` | 차체 실측 — 같은 설계면 동일 |
| WiFi 자격증명 | netplan | 설치 장소마다 다름 |

**2호기에 그대로 이미지를 구우면 1호기의 보정값으로 달린다.** 직진이 틀어지고,
라이다 필터가 엉뚱한 각도를 자르고, 회전 토크가 안 맞는다. 조용히 잘못 동작하기
때문에 원인 찾기도 어렵다.

### 제안 구조

```
/etc/smart-trash/
├── unit.yaml          # 식별자: unit_id(파이 시리얼), 이름, 제작일, 하드웨어 리비전
├── calibration.yaml   # 실측 보정값: straight_trim, turn_boost, 라이다 차폐 구간 등
└── site.yaml          # 설치 환경: WiFi, 맵 이름, 금지구역
```

- 이 세 파일은 **이미지에 포함하지 않는다.** 첫 부팅 프로비저닝이 생성한다.
- 코드는 이 파일이 없으면 **안전한 기본값으로 동작하되 경고를 남긴다**
  (`straight_trim=0`처럼 보정 없는 상태 — 틀리게 가는 것보다 낫다).
- 백업 대상은 이 세 파일뿐이다. 나머지는 전부 재생성 가능하다.

## 3. 프로비저닝 — 2호기를 어떻게 만드나

```
1. 베이스 이미지를 카드에 굽기                          (~10분)
2. 첫 부팅 → 프로비저닝 서비스가 자동 실행
   a. unit_id 생성 (파이 시리얼 /proc/cpuinfo 기반, 고유·불변)
   b. 호스트명 설정 (smart-bin-02)
   c. WiFi 자격증명 입력 받기 (또는 site.yaml 주입)
   d. 저장소 최신 태그로 업데이트 + colcon build
3. 보정 절차 실행                                       (~30분, 사람 필요)
   a. 라이다 차폐 스캔 → 차폐 구간·range_min 산출
   b. 직진 트림 cliff test → straight_trim 산출
   c. 회전 토크 시험 → turn_boost 산출
   d. → calibration.yaml 저장
4. 자가진단 후 운용 개시
```

3번을 **자동화된 보정 마법사**로 만드는 게 이 체계의 핵심 투자다. 1호기에서는
이걸 손으로 하느라 여러 시간이 걸렸다. 스크립트로 만들면 유닛당 30분으로 줄고,
무엇보다 **사람이 잊어버리지 않는다.**

### 베이스 이미지 만들기

- 실사용 15GB이므로 이미지를 **축소해서 배포**한다(파티션을 실사용+여유로 줄인 뒤
  이미지 추출, 첫 부팅에 자동 확장). 128GB 통이미지를 옮기는 건 비현실적이다.
- 이미지에서 **반드시 지울 것**: SSH 호스트키(유닛마다 새로 생성돼야 함),
  machine-id, WiFi 자격증명, `/etc/smart-trash/*`, 로그, 셸 히스토리, git 인증정보.
- 버전은 `image-v1.0` 형태로 태그하고, 어떤 저장소 커밋으로 빌드했는지 기록한다.

## 4. 업데이트와 롤백

### 애플리케이션 (일상)

```
git fetch → 릴리스 태그로 checkout → colcon build → 서비스 재시작 → 자가진단
```

- 실패하면 **직전 태그로 자동 복귀**. 이게 롤백의 전부다.
- 자율주행 중에는 업데이트하지 않는다(주행 상태 확인 후 진행).
- 네트워크가 불안정한 환경이므로 **원자적으로** 진행 — 빌드가 끝나고 검증까지
  통과한 뒤에 서비스를 바꾼다. 중간 상태로 남으면 안 된다.

### OS 이미지 (드묾)

소규모 플릿에서는 **카드 교체가 가장 확실한 OTA**다. 새 이미지를 구운 카드를
꽂고, 유닛 설정 3개 파일만 복원하면 끝난다. 실패 시 이전 카드를 다시 꽂으면 되므로
롤백이 물리적으로 보장된다.

> 장래에 진짜 무인 OS 업데이트가 필요해지면 라즈베리파이의 `tryboot`을 쓸 수 있다.
> A/B 루트 파티션을 두고 `reboot '0 tryboot'`으로 새 쪽을 시험 부팅하며, 확정하지
> 않으면 다음 부팅에 자동으로 원래대로 돌아온다. 지금 규모에는 과하다.

## 5. 텔레메트리 — 무엇을 왜 모으나

목적은 두 가지다. **(a) 잘못된 사용으로 수명이 깎이는 걸 막는 것, (b) 유닛 간
비교로 최적화 근거를 얻는 것.**

### 수집 항목

| 분류 | 항목 | 왜 |
|---|---|---|
| **수명** | 누적 기록량(`written_mb`), 일일 증가율, 가동시간, 전원 사이클 수 | SD는 SMART가 없어 이게 유일한 수명 지표 |
| **안정성** | 프리즈 발생, D상태 정체(`stuck`) 건수와 wchan, 비정상 종료 횟수 | 오늘 같은 사고의 조기 발견 |
| **전원** | 전압 프로파일, 스로틀 비트, 배터리 방전 곡선 | 방전·전압강하 사고가 이미 2회 |
| **주행** | 복구동작(spin/backup) 발동 횟수, 경로계획 실패율, 갇힘 사건 위치 | 주방 갇힘 같은 문제를 지도 위에 누적 |
| **센서** | 라이다 차폐 비율, 스캔 유효 포인트 비율 | 구조물이 틀어지면 여기서 드러남 |
| **통신** | 위치별 WiFi 신호 세기 | 음영지역 파악 |

### 설계 제약 — 이 로봇의 현실

1. **자주 오프라인이다.** WiFi 음영지역(주방)이 실재한다. → 로컬에 버퍼링하고
   신호가 좋을 때 기회적으로 업로드. 업로드 실패가 로봇 동작에 영향을 주면 안 된다.
2. **로깅 자체가 수명을 깎는다.** 수명을 재려고 카드를 닳게 하는 건 본말전도다.
   → 고빈도 원시 데이터는 tmpfs(메모리)에 두고, **요약본만** 주기적으로 카드에 쓴다.
3. **작아야 한다.** 유닛 3대 규모에 카프카 같은 건 필요 없다. 압축된 일일 요약
   파일을 HTTP나 rsync로 올리는 정도면 충분하다.

### 서버 쪽

- 유닛별 시계열 보관 + 유닛 간 비교
- 알림: 일일 쓰기량 급증, `stuck` 발생, 전압 이상, 복구동작 급증
- **유닛 간 비교가 진짜 가치다.** 2호기만 복구동작이 많다면 그건 소프트웨어가
  아니라 그 개체의 기계적 문제다. 1대로는 절대 알 수 없는 정보다.

## 6. 카드 수명 관리

### 현재 수치와 여유

유휴 3.05 GB/day 중 대부분이 개발 도구다. **배포 유닛 기준 추정치는 별도로
측정해야 한다**(IDE 없는 상태에서 재측정 필요).

128GB 소비자용 microSD의 실질 총 기록 한계는 사양에 명시되지 않는 경우가 많다.
따라서 절대 수명을 계산하려 하기보다, **일일 쓰기량의 추세와 급변을 감시**하는 게
현실적이다. 평소의 3배가 되면 뭔가 잘못된 것이다.

### 쓰기 감축 (효과 큰 순서)

1. **ROS 로그를 tmpfs로.** 세션 디버그용이라 재부팅 후 남을 이유가 없다.
2. **journald를 축소.** 블랙박스가 이미 영구 기록을 담당하므로 중복이다.
3. **`power_trace.csv`를 배치 기록으로.** 지금 1Hz + 5초마다 fsync인데,
   메모리에 모았다가 덜 자주 쓰면 된다.
4. **블랙박스를 링버퍼로.** 지금 1Hz + 2초마다 fsync다. 평소엔 메모리 링버퍼에
   두고 **이상 징후(`stuck>0`)가 보일 때만** 즉시 카드에 쏟아내면, 포렌식 가치는
   그대로 두고 쓰기를 대폭 줄인다.
5. **개발 유닛은 IDE 서버 캐시를 tmpfs나 외장으로.** 204 MB/h의 주범.

> ⚠️ SD는 작은 쓰기 하나가 큰 소거 블록 전체를 프로그램하게 만들 수 있다
> (쓰기 증폭). **fsync 빈도가 총 바이트 수보다 더 중요할 수 있다.** 위 항목들이
> 모두 "덜 자주 쓰기"에 초점을 맞춘 이유다.

### 교체 정책

SD를 소모품으로 다루려면 **교체가 쉬워야** 한다. 위 3계층 모델이 그걸 보장한다 —
카드가 죽어도 잃는 건 유닛 설정 3개 파일뿐이고, 그건 서버에 백업돼 있다.
새 카드에 이미지를 굽고 설정을 복원하면 30분 안에 복귀한다.

## 7. 단계별 실행 계획

지금 당장 전부 만들 필요는 없다. 가치 대비 비용 순으로.

| 단계 | 내용 | 왜 이 순서인가 |
|---|---|---|
| **1** | 유닛 설정 3파일 분리 (`/etc/smart-trash/`) + 코드가 이를 읽도록 수정 | **2호기를 만들기 전에 반드시 끝나야 한다.** 안 하면 1호기 보정값으로 달린다 |
| **2** | 쓰기 감축 (위 1~4번) + 배포 유닛 기준 쓰기량 재측정 | 지금 카드를 지키는 일. 즉시 효과 |
| **3** | 텔레메트리 로컬 수집 + 일일 요약 파일 생성 | 서버가 없어도 가치 있음. 데이터가 쌓이기 시작해야 나중에 비교가 가능 |
| **4** | 보정 마법사 자동화 | 2호기 제작 직전에 필요 |
| **5** | 베이스 이미지 빌드·축소 절차 정립 | 2호기 제작 시점 |
| **6** | 서버 수집·비교 대시보드 | 유닛이 2대 이상이 된 뒤에야 의미가 생김 |
| **7** | (선택) `tryboot` A/B 무인 OS 업데이트 | 유닛이 손 닿지 않는 곳에 놓일 때 |

**1번과 2번은 지금 해도 되고, 나머지는 2호기 제작이 구체화될 때 하면 된다.**
특히 6번을 먼저 만들고 싶은 유혹이 있지만, 비교할 유닛이 1대뿐이면 얻는 게 없다.
