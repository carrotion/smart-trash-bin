# 로봇 ↔ 서버 통신 규약 — 0.2판 (2026-11-14, 설계 단계·로봇 쪽 구현 전)

서버와 연동해서 미션을 하기 위한 약속이에요. 로봇 쪽은 이 저장소, 서버 쪽은 서버 개발 담당이 맡아요.
역할 경계는 `docs/agent_architecture.md`(1절 원칙, 7절 엣지 우선 설계)를 따릅니다.

- **0.1판 → 0.2판**: 서버 개발 담당의 검토 12건(C1~C12)과 서버 쪽 1차 구현을 반영했어요. 바뀐 곳마다 `[C번호]`를 붙였어요. 변경 목록은 맨 끝에 있어요.
- **전제가 바뀌었어요(11-14)**: 사람과 말로 대화하는 상대는 서버의 대화 AI예요. 로봇은 그 AI의 장치(귀, 입, 눈, 다리) 중 하나예요. 무엇을 할지는 서버가 정하고, 로봇은 할 수 있는지만 판단해요(1절 2번). 이 규약은 로봇과 서버 사이만 다뤄요. 대화 AI의 내부, 목소리 등급, 손님 처리는 서버 설계 문서에 있어요. [C11]

## 1. 지키는 것

1. **로봇은 서버를 기다리지 않는다.** 서버가 없어도 하던 일을 계속하고, 보낼 것은 쌓아 뒀다가 나중에 보낸다.
2. **서버는 시키고, 로봇은 할 수 있는지만 판단한다.** 할 수 없는 상태면 이유를 붙여 거절한다. 거절 이유는 배터리, 비상정지 중, 자리 검사 실패, 금지 구역, 장치 없음 다섯 가지다. 누구의 말을 들어줄지는 서버가 걸러서 보낸다. 로봇은 말한 사람을 따지지 않는다.
3. **안전은 로컬에서 한다.** 비상정지, 장애물, 속도 단위 조종은 서버를 거치지 않는다.
   - "멈춰"도 로봇에 마이크가 달리면 로봇이 직접 알아듣고 선다(3.5절). 서버의 `cancel`은 보조다. [C4]
4. **명령마다 고유 번호와 유효 시간을 단다.** 같은 번호를 두 번 받아도 한 번만 한다.
   - 유효 시간이 지난 명령은 하지 않는다. 통신이 밀렸다가 한꺼번에 오는 경우에 대비한 것이다.
   - 두 기기 사이의 시각은 비교하지 않는다. 시간은 늘 "받은 때부터 몇 초"로 주고받고, 로봇은 자기 단조 시계로 센다. [C1]
5. **받음, 시작, 끝을 따로 알린다.** 끝에는 결과를 정해진 값으로 붙인다(3.3절). [C5]

## 2. 길

- **Tailscale**을 쓴다. 집 안에서는 Wi-Fi로 직접 이어지고, 덧붙는 왕복 시간은 1 ms 미만이다(11-14 실측). 서버는 자기 Tailscale 주소에만 받는 곳을 연다.
- **HTTP + JSON.** 사진과 음성은 base64로 본문에 싣는다.
  - 사진 한 장은 10~70 KB, 음성 5초는 약 160 KB다. base64로 1/3이 늘어도 집 안 Wi-Fi에서는 문제가 안 된다. 서버도 이미 이 방식으로 만들었다.
  - 음성을 끊김 없이 흘려보내야 할 때 원본 본문이나 WebSocket을 다시 본다. [C9]
- **연결은 로봇이 건다.** 로봇은 받는 곳을 열지 않는다. 서버 명령은 로봇이 오래 기다리는 요청(long-poll)으로 받아 간다.
- **인증**: 요청마다 `Authorization: Bearer <기기 토큰>`을 붙인다. [C10]
  - 토큰은 파이의 사용자 전용 파일(권한 600, 저장소 밖)에 둔다. 저장소, 보관함, 로그에는 쓰지 않는다.
  - 토큰을 바꿀 때: 서버가 새 토큰을 더한다 → 두 토큰이 함께 유효한 동안 로봇 파일을 바꾼다 → 서버가 옛 토큰을 지운다.
  - Tailscale 접근 규칙은 두지 않는다. 같은 망의 다른 기기는 사용자가 등록한 것이다(11-14 사용자).

### 받는 곳 (서버 1차 구현을 규약으로 삼음)

| 로봇이 부르는 것 | 하는 일 |
|---|---|
| `POST /v1/robots/{기기}/hello` | 능력 목록(3.1절). 켤 때, 능력이 바뀔 때, 서버가 다시 달라고 할 때 |
| `GET /v1/robots/{기기}/commands?timeout=20` | 명령 받기(long-poll). 명령이 없으면 204 |
| `POST /v1/robots/{기기}/ack` | 명령 진행 알림 |
| `POST /v1/robots/{기기}/status` | 상태 |
| `POST /v1/robots/{기기}/event` | 사건 |
| `POST /v1/robots/{기기}/infer` | 판정 맡기기(답을 기다림) |
| `POST /v1/robots/{기기}/hear` | 들은 소리 올리기(답을 기다리지 않음) — **새로 필요** [C3] |
| `POST /v1/robots/{기기}/seen` | 본 사람 올리기(답을 기다리지 않음) — **새로 필요**, 깊이 카메라를 단 뒤 [C12] |

명령 넣기, 장부 읽기처럼 서버 안쪽에서 쓰는 것은 서버 문서에 있다.

## 3. 주고받는 것

### 3.1 `hello` — 능력 목록 (로봇 → 서버) [제안 1, C7]

서버(대화 AI)는 이 목록만 보고 로봇에게 줄 명령을 만든다. 그래서 다른 로봇이 붙어도 서버를 고치지 않는다.

```json
{"protocol": "0.2", "software": "dac0801", "caps_version": "c3f9",
 "name": "쓰레기통",
 "devices": {"mic": false, "speaker": false, "camera": false},
 "commands": {
   "go_to":       {"args": {"place": "장소 이름", "x": "m", "y": "m"}, "rejects": ["battery", "estop", "pose_check", "keepout"]},
   "return_home": {"args": {}, "rejects": ["estop"]},
   "cancel":      {"args": {"id": "명령 번호(없으면 지금 하는 것)", "target": "mission|speech|all"}, "rejects": []},
   "get_status":  {"args": {}, "rejects": []},
   "plan":        {"args": {"steps": "명령 목록(최대 8)"}, "rejects": ["처음부터 거절 사유가 있는 단계가 하나라도 있으면 통째로"]}
 },
 "places": []}
```

- `commands`에는 **지금 할 수 있는 것만** 넣는다.
  - `say`와 `ask`는 스피커와 마이크를 단 뒤에 넣는다. 그 전에 오면 `device` 이유로 거절한다.
  - `explore`는 저장 지도로 다니는 동안에는 빼고, 지도를 새로 그릴 때만 넣는다.
- `caps_version`은 목록 내용으로 만든 짧은 해시다.
  - `status`마다 이 값을 싣는다. 서버가 가진 값과 다르면 서버는 `status`에 `409`로 답하고, 로봇은 `hello`를 다시 보낸다.
- `places`(이름 붙인 장소)는 아직 비어 있다. 저장 지도에 장소 이름을 붙이는 일은 따로 정한다. 그 전까지 `go_to`는 좌표만 쓴다.
- 부르는 말(호출어)은 서버 설정이다. 이 목록에 싣지 않는다. 로봇에 마이크가 달리면 서버가 정한 말을 로봇 설정에 넣는다.

### 3.2 `command` — 명령 (서버 → 로봇, long-poll 응답)

```json
{"id": "cmd_ab12cd34ef56", "type": "go_to", "args": {"x": 2.2, "y": -1.5},
 "source": "voice", "ttl_s": 29.8}
```

- **`ttl_s`**: 로봇이 받은 순간부터 이 초가 지나면 하지 않는다. 시작 전에 지나면 `finished/expired`로 알린다.
  - 이미 시작한 명령은 유효 시간이 지나도 계속한다. 유효 시간은 "언제까지 시작해도 되나"이다. [C1]
- 서버는 `received`가 올 때까지 5초마다 같은 명령을 다시 준다. 로봇은 번호로 중복을 거른다.
  - 로봇은 본 번호를 최근 200개까지 기억한다. 켤 때 비우는데, 그 사이 다시 온 옛 명령은 `ttl_s`가 막는다.
- **명령 목록**:

| 명령 | 인자 | 로봇이 하는 일 | 거절 |
|---|---|---|---|
| `go_to` | `place` 또는 `x`, `y` | 저장 지도 위 그 자리로 간다 | `battery`(1차 하한 아래), `estop`, `pose_check`(자리 검사 실패), `keepout`(목표가 금지 구역 안) |
| `return_home` | — | 출발점(충전 자리)으로 간다 | `estop` |
| `explore` | `start` / `stop` | 탐색을 시작하거나 멈춘다 | `map_mode`(저장 지도로 다니는 중) |
| `cancel` | `id`(없으면 지금 하는 것), `target` = `mission`·`speech`·`all`(기본 `all`) | 미션을 그만두고 선다, 말을 멈춘다, 또는 둘 다. 비상정지가 아니다 [C2] | — |
| `say` | `text`, `interrupt`(기본 false) | 스피커로 말한다. `interrupt`면 하던 말을 끊고 말한다 | `device` |
| `get_status` | — | 바로 `status`를 보낸다 | — |
| `ask` | `text`, `listen_s` | 그 말을 하고 대답을 들어 `hear`(이 명령 번호를 단 것)로 보낸다. 대답이 없으면 `finished/failed(no_answer)`로 끝난다 | `device` |
| `plan` | `steps`(명령 목록, 최대 8) | 차례로 한다 [C6] | 처음부터 거절 사유가 있는 단계가 하나라도 있으면 통째로 |

- **`plan`의 경계** [C6]
  - `plan` 안에는 `go_to`, `return_home`, `say`만 넣는다. `plan` 안의 `plan`, `ask`, `explore`, `cancel`은 거절한다.
  - `ask`를 빼는 까닭: 대답에 따라 다음 단계가 바뀌면 그것은 미리 정한 목록이 아니다. 되묻기는 서버가 `ask`로 먼저 하고, 대답을 들은 뒤 `plan`을 보낸다.
  - 단계 하나가 실패하거나 거절되면 나머지는 하지 않는다.
  - 진행 중에 `cancel`이 오면 남은 단계까지 버린다.
  - 마지막 알림에 몇 번째 단계에서 멈췄는지(`step`, 0부터)를 싣는다.

### 3.3 `ack` — 명령 진행 (로봇 → 서버) [C5]

```json
{"id": "cmd_ab12cd34ef56", "phase": "finished",
 "result": {"outcome": "failed", "reason": "경로가 뒤집혀 왕복 중", "step": 1}}
```

| `phase` | 언제 | 덧붙는 것 |
|---|---|---|
| `received` | 받은 즉시 | — |
| `rejected` | 하지 않기로 했을 때 | `reason`: `battery`·`estop`·`pose_check`·`keepout`·`device`·`map_mode`·`invalid` |
| `started` | 시작할 때 | `plan`이면 단계마다 `step` |
| `finished` | 끝났을 때 | `result.outcome`: `done`·`failed`·`canceled`·`expired`, `reason`(실패면 주행기 문구 그대로), `step`(`plan`일 때) |

- 모든 명령은 `rejected`나 `finished` 중 하나로 반드시 끝난다. `cancel`을 맞은 명령도 `finished/canceled`를 보낸다.
- `cancel` 자신도 `received` → `finished/done`으로 끝난다.
- 서버 쪽 대응: `outcome`이 `done`이면 서버 상태 `done`이고, 나머지는 `failed`이며 `outcome`은 그대로 남긴다. 서버가 쓰는 `result.ok`는 `outcome == "done"`과 같다. 둘 다 싣는다.
- 보내다 실패하면 쌓아 뒀다가 다시 보낸다. 서버는 같은 명령의 마지막 알림으로 덮는다.

### 3.4 `status` — 상태 (로봇 → 서버) [C7]

5초마다, 그리고 모드가 바뀌면 바로 보낸다.

```json
{"protocol": "0.2", "software": "dac0801", "caps_version": "c3f9", "boot_id": "…", "uptime_s": 3812.4,
 "robot_time": "2026-11-14T19:10:02+09:00",
 "mode": "idle", "pose": {"x": 1.79, "y": -2.78, "yaw_deg": 12.0, "map": "home_20261114_explore9"},
 "battery": {"v": 12.07, "stage": "ok"},
 "doing": null, "speaking": false,
 "devices": {"mic": false, "speaker": false, "camera": false},
 "cpu_pct": 23, "mem_avail_mb": 2700,
 "link": {"rtt_ms_p50": 7.9, "lost_pct": 0.0, "wifi_dbm": -48, "path": "edge_ok"}}
```

- `mode`: `idle`·`mission`·`explore`·`charging`·`estop`. `doing`은 하고 있는 명령 번호.
- `robot_time`은 비교용이 아니라 알아채기용이다. 서버가 자기 시계와 크게 다르면 기록만 남긴다. 판단에는 쓰지 않는다. [C1]
- `link.path`: 엣지 우선 판정의 지금 자리. 바뀔 때는 `event`로 이유와 함께 알린다(3.6절). [E4]

### 3.5 음성 — 로봇이 할 일만 [C2, C3, C4, C11, E1]

로봇에 마이크와 스피커는 깊이 카메라와 함께 단다. 그 전에는 서버 쪽 장치로 서버가 따로 시험한다. 서버 시험의 문장 목록과 잴 것은 서버 설계 문서로 옮겼다.

- **로봇은 귀와 입이다.** 로봇이 하는 일은 세 가지다.
  - 엣지에서 호출어와 말 구간만 알아챈다.
  - 들은 소리를 `hear`로 올린다.
  - 서버가 `say`·`ask`로 준 말을 한다.

  뜻을 이해하는 것과 누구 목소리인지 가리는 것은 서버가 한다.
- **`hear`** (로봇 → 서버, 답을 기다리지 않음):
  ```json
  {"audio_b64": "…", "format": "pcm_s16le_16k_mono", "heard_ago_ms": 420,
   "trigger": "wake", "reply_to": null, "mic": "로봇 마이크 이름"}
  ```
  - `trigger`: `wake`(호출어), `ask`(이때 `reply_to`에 그 `ask` 명령 번호), `button`.
  - `heard_ago_ms`: 말이 끝난 때부터 보낼 때까지 걸린 시간. 시각 대신 경과 시간을 쓴다. [C1]
  - 대답은 `hear`의 응답으로 오지 않고 `say`·`command`로 따로 온다. 그래서 `infer`(로봇이 답을 기다리는 판정)와 나눈다. [C3]
- **"멈춰"는 로봇이 직접** [C4]
  - 엣지가 작은 말 목록("멈춰", "그만", "정지")을 늘 듣는다. 호출어가 없어도 되고, 누가 말해도 된다.
  - 들리면 미션과 말을 둘 다 멈추고(`cancel target=all`과 같다) `event: local_stop`을 보낸다.
  - 서버도 같은 말을 들으면 `cancel`을 보낸다. 로봇이 이미 서 있으면 `finished/done`으로 끝난다.
- **통신이 끊기면** [E1]
  - 대화 상대가 서버에 있으므로, 엣지는 대화를 대신하지 않는다.
  - 엣지가 직접 알아듣는 것은 "멈춰"류(위)와 "돌아가"류(`return_home`) 두 가지뿐이다.
  - 그 밖의 말에는 미리 만들어 둔 음성으로 "지금은 연결이 안 돼요"라고만 답한다.
- **부르는 말이냐 버튼이냐**는 아직 정하지 않았다. 로봇에서는 호출어를 엣지에서 듣는 것이 맞다(엣지 우선 7절의 가벼운 일). 버튼은 `trigger: button`으로 이미 자리가 있다.

### 3.6 `event` — 사건 (로봇 → 서버) [C8]

```json
{"event_id": "<boot_id 앞 8자>-000123", "kind": "mission_failed", "ago_ms": 0, "data": {"id": "cmd_…", "reason": "…"}}
```

- `event_id` = 부팅 번호(`/proc/sys/kernel/random/boot_id` 앞 8자) + 부팅 뒤 일련번호. 서버는 같은 번호를 한 번만 받는다.
  - 쌓아 뒀다 보낼 때는 일련번호 순서대로 보낸다.
  - `ago_ms`는 일이 난 때부터 보낸 때까지의 경과 시간이다.
- `kind`:
  - 미션: `mission_arrived`, `mission_failed`(이유는 주행기 문구 그대로)
  - 안전: `stuck`, `estop`, `local_stop`
  - 전원과 보드: `battery_stage`, `board_silent`
  - 엣지 우선: `path_changed`(엣지와 서버 사이를 옮김 — 이유: CPU·메모리·배터리·통신, 그때 숫자) [E4]

### 3.7 `infer` — 판정 맡기기 (로봇 → 서버, 답을 기다림)

- 지금은 `kind: "people"`(사진 한 장 → 사람 수와 상자)만 있다. 엣지 우선 설계 7절에서 "버거움 + 통신 좋음"일 때만 쓴다.
- 요청에 **`budget_ms`**(이만큼 안에 답이 와야 쓸모 있음)를 싣는다. 로봇은 보낸 때부터 자기 시계로 세고, 넘으면 답을 버리고 엣지에서 다시 한다. 서버는 늦었는지(`late`)를 알려 준다. [C1]
- 사진은 서버도 로봇도 저장하지 않는다.

### 3.8 `seen` — 본 사람 (로봇 → 서버, 깊이 카메라를 단 뒤) [C12]

- 로봇이 엣지에서 사람을 찾으면 그때만 얼굴 부분을 잘라 보낸다. 누구인지는 서버가 가린다.
  - 서버의 대화 AI는 주인이 보일 때만 먼저 말을 건다. 로봇 카메라도 그 단서가 된다.
- 내용: 얼굴 부분 사진(JPEG), 화면 속 상자, `ago_ms`, 로봇 자세, 카메라 이름.
- 같은 사람(같은 추적 번호)은 2초에 한 번까지만 보낸다. 얼굴이 안 보이면(다리만 보이는 장면) 보내지 않는다. 로봇은 사진을 저장하지 않는다.
- 통신이 끊기면 보내지 않고 버린다. 쌓아 두지 않는다. 누구인지 모르는 동안은 손님으로 대한다(엣지 우선 7절). [E2]

## 4. 정할 값 — 파이에서 재서 정한다

| 값 | 잠정 | 정하는 법 |
|---|---|---|
| long-poll 기다리는 시간 | 20초 | 파이에서 가짜 로봇으로 명령 전달 시간을 잰다: 기다리는 중에 넣은 명령, 다시 거는 틈에 넣은 명령(중앙·90%). Wi-Fi가 약한 드레스룸에서도 |
| `status` 주기 | 5초(서버 잠정 60초) | 서버가 로봇을 "끊김"으로 보는 기준(`stale_after_s`)과 함께 정한다. 끊김을 3번 놓쳐야 끊김으로 본다 |
| 명령 기본 `ttl_s` | 30초 | 위 전달 시간의 99%보다 넉넉히 |
| 다시 주기 간격 | 5초(서버) | 위 전달 시간을 보고 |
| `infer` `budget_ms` | 사람 인식 300 ms | 엣지 101 ms의 세 배. 실제 왕복(사진 크기별)을 재고 고친다 |

- 9번째 탐색에서 잰 집 안 왕복(ICMP): 중앙 7.9 ms, 90% 14.7 ms, 99% 307 ms. 느린 것과 잃은 것은 드레스룸(−68 dBm)에 몰렸다. HTTP 왕복은 받는 곳에서 다시 잰다.
- 인터넷이 끊겼을 때 Tailscale의 집 안 직접 연결이 유지되는지 확인한다. 끊기면 집 Wi-Fi 주소로 내려가는 길이 필요하다(검토 P4).
